# Cross-volume transfer design

상태: 전송 자료형·상태 검증·SQLite 기록 기반, Windows 임시 복사/검증·최종 이름 확정, 기록 연결과 세 위치 읽기 전용 복구 검사를 구현했다. 원본 제거·다른 볼륨 되돌리기는 아직 구현하거나 활성화하지 않았다. 현재 앱 실행기는 같은 볼륨의 덮어쓰기 없는 이름 변경만 지원한다.

## 현재 구현된 기반

- `include/nookbit/domain/transfer.hpp`: 전송 방향·단계·시도·갱신 요청. 객체 동일성 검사와 내용 동일성 검사를 분리한다.
- `include/nookbit/application/transfer_journal.hpp`: 파일 작업과 분리된 `ITransferJournal` 계약.
- `SqliteTransferJournal`: 예상 이전 단계 검사, 단계에 맞는 지문·오류 증거 검사, 스냅샷과 이벤트의 원자적 기록, 이벤트 재생으로 재시작 복원.
- Schema v2: `transfer_attempts`·`transfer_events`를 추가한다. 기존 계획·승인·해시 형식 v1은 변경하지 않는다. 실행 중인 단계에만 시도를 연결하고 미해결 시도의 중복 시작을 막는다.
- SQLite 이행: 버전순 마이그레이션, 실패 시 해당 이행 롤백, 지원 버전보다 높은 DB의 쓰기 거부.
- `transfer_journal_tests.cpp`: 정상 단계 전이, 잘못된 순서·증거·중복·낡은 갱신 거부, 정방향/역방향 별도 기록, 재시작 복원, 이벤트 저장 실패 원자성, 이전 DB·해시 보존, 이행 실패/재시도·더 높은 버전 거부를 검사한다.

`StagingCreated`는 임시 파일 생성 후 객체 ID를 기록하는 별도 단계다. 현재 저널의 `Completed`는 호출자가 보고한 전송 시도의 기록 상태이지 실제 파일 이동 완료를 보증하지 않는다. 기존 `StepStatus`·계획 완료를 자동 갱신하지 않는다. 원본 제거 권한도 제공하지 않는다. 파일 일꾼·저널·상위 이동 완료를 결합하는 작업은 후속 구현에서 수행한다. 계획 서명 v2·원본 제거 세션・복구 결과의 명시적 기록 정리는 아직 남아 있다.

### 임시 복사 일꾼의 현재 범위

- `application/staged_copy.hpp`의 포트와 `WindowsStagedCopy` 어댑터를 추가했다. SQLite·UI를 모르며 원본 삭제 API를 제공하지 않는다. 검증된 세션만 임시 파일을 같은 부모의 최종 이름으로 확정할 수 있다. 아직 앱 실행기에 연결하지 않았다.
- 볼륨 조회는 없는 경로의 가까운 기존 조상에서 일련번호·볼륨 GUID·파일 시스템을 읽고 폴더를 만들지 않는다. 세션은 기존 부모 폴더만 받으며, 원본과 부모 경로를 핸들로 보호한다. 잠금 불가·경로 접근 불가도 실패다.
- `open`은 원본 객체 ID·크기·수정 시각·SHA-256과 지원 범위를 검사하고 `CREATE_NEW`로 빈 임시 파일을 만든다. 호출자는 반환된 `createdFingerprint`를 `StagingCreated`로 저장한 뒤 `copyAndVerify`를 호출해야 한다. 기록 실패 시 복사를 진행하지 않는다.
- 복사는 1MiB 버퍼로 한 번만 수행하며 flush 후 임시 파일을 다시 읽어 해시를 계산한다. 원본도 다시 검증하고 생성/수정 시각·기본 속성을 보존·검사한다. 대상 ACL은 대상 폴더에서 상속한다.
- 실패·취소·세션 해제 시 원본이나 임시 파일을 자동 삭제하지 않는다. 빈 파일 생성 뒤 지문 조회가 실패한 경우도 파일명으로 소유권을 추정하지 않는다. 향후 저널 기반 복구가 다뤄야 한다.
- 현재는 고정 로컬 NTFS의 일반 단일 링크 파일만 받는다. ADS·EFS·재분석 지점·오프라인/회수 속성·압축·희소 파일·부모 재분석 지점(폴더 마운트 포함)은 거부한다. 압축/희소 처리와 제거 권한은 별도 설계 전까지 제공하지 않는다.
- 이번 실제 파일 테스트는 한 볼륨의 임시 폴더에서 복사·확정 원시 작업과 DB 경계 연동을 검사했다. 두 드라이브 전송 완료·공간 부족·실제 읽기/쓰기 장애·볼륨 분리는 아직 검증하지 않았다.

### 복사본 확정과 기록 연결

`CommitTransferCopyUseCase`는 외부에서 주입받은 복사·저널 포트로 `Prepared → CopyIntent → StagingCreated → CopyVerified → CommitIntent → DestinationCommitted`를 수행한다. 파일 일꾼끼리 직접 호출하거나 SQLite를 파일 일꾼 내부에서 사용하는 구조는 아니다. 승인·경로 정책·계획 서명 v2 검증을 대체하는 진입점이 아니며, 실제 앱 흐름에서는 아직 호출하지 않는다.

- 모든 파일 작업은 앞선 의도/증거 저장 성공 뒤에만 수행한다. 생성 지문 기록 실패에는 복사를 시작하지 않고, 확정 의도 기록 실패에는 이름을 바꾸지 않는다.
- 세션의 `commitNoReplace`는 복사 검증 성공 후 한 번만 허용한다. 원본·임시 파일 내용과 기본 메타데이터를 재검사하고 보유한 임시 파일 핸들의 `FileRenameInfo`로 같은 부모 안에서만 이름을 바꾼다. `ReplaceIfExists=FALSE`이며 최종 경로의 기존 파일을 덮어쓰지 않는다. 확정 후 flush와 객체·내용·메타데이터를 재검사한다.
- Windows `DELETE` 접근 권한은 임시 파일 핸들의 이름 변경에 필요해 그 핸들에만 부여한다. 원본 핸들에는 부여하지 않으며 파일 제거/삭제 예약 API는 사용하지 않는다. 이 접근 권한과 프로그램의 원본 삭제 허가는 다른 개념이다.
- 읽기 전용·숨김 원본의 테스트에서 NTFS 이름 변경이 보관 속성을 추가하는 것을 확인했다. 확정 뒤 보존할 기본 메타데이터를 재적용하고 검사하여 이 변경도 처리한다. 재적용 실패는 원본을 유지한 채 복구 필요로 남긴다.
- 취소는 확정 의도 기록 전까지만 반영한다. 확정 의도 기록 뒤에는 결과 판정과 기록을 끝내고, 불확실한 결과를 단순 취소로 숨기지 않는다.
- 생성 실패는 생성 뒤 지문 조회 실패일 수도 있어 보수적으로 `NeedsRecovery`로 남긴다. 복사 실패/취소는 `Failed`/`Cancelled`로 기록하고 원본·부분 복사본을 보존한다. 기록 실패·확정 오류·확정 후 결과 저장 실패는 `NeedsRecovery`를 시도한다. 복구 필요 기록도 실패하면 오류를 반환하며 마지막 미해결 단계가 재시도를 막는다.
- 성공 반환은 `DestinationCommitted`이지 `Completed`가 아니다. 원본은 그대로 있고 상위 `StepStatus`·계획은 실행 중이다. 이 유스케이스 종료 시 핸들은 닫히며 원본 제거 단계로 자동 이어지지 않는다. 향후 전체 전송 조율에서는 검증부터 원본 제거까지 세션 수명·권한을 별도로 통합해야 한다.
- `commit_transfer_copy_tests.cpp`는 실제 SQLite 재열기와 임시 NTFS 파일로 정상 확정, 각 저장 경계의 실패, 지속적인 DB 쓰기 실패, 확정 직후 API 오류 주입, 이름 충돌, 취소, 중복/미해결 시도 거부와 원본 보존을 검사한다. OS 강제 종료·전원 차단·두 볼륨의 전체 전송 시험은 아니다.

## 읽기 전용 전송 복구 검사

`InspectTransferRecoveryUseCase`는 저널 시도 하나를 다시 읽고, 기존 계획 서명·단계 ID·정방향/역방향 경로·원본 내용 연결을 검증한 뒤 세 위치를 검사한다. 신뢰할 수 없는 계획은 임의 경로를 읽지 않고 `UntrustedRecord`로 반환한다. 저널 손상이나 읽기 실패는 오류로 반환한다. 파일 작업이나 전송/상위 상태 쓰기는 제공하지 않는다.

`WindowsTransferFileInspector`는 복사 일꾼과 별도의 포트 구현이며 읽기 전용 Windows 헬퍼만 공유한다. 안전한 기존 조상에서 볼륨을 확인하고 보호된 핸들로 객체·내용을 읽는다. 지원하지 않는 파일·부모 재분석 지점·쓰기 잠금·접근 불가를 `Unavailable`로 반환하며 폴더나 파일을 생성하지 않는다.

- 세 파일 상태: `Missing`, `Matches`, `ObjectOnly`(생성 ID만 일치하고 완전한 내용 검증 기록 없음), `Unowned`, `Changed`, `OtherVolume`, `Unavailable`.
- 같은 내용의 새 파일도 객체 ID가 다르면 `Unowned`다. 검증 전 임시 파일 이름만으로 소유권을 인정하지 않는다. 기록된 볼륨과 다른 위치나 분리된 드라이브를 원본 없음으로 취급하지 않는다.
- 결과: 복사본 미관찰, 미검증 임시 객체, 검증된 임시 복사본, 원본과 기록된 최종 복사본이 함께 남음, 최종 경로에 검증된 임시 객체가 있지만 확정 결과 기록 없음, 제거 의도 이후 원본 없음, 변경/소유권 불명, 모호함, 확인 불가, 기록 신뢰 불가. 각 결과에 설명과 관찰 오류를 제공한다.
- `SourceAbsentAfterRemoveIntent`도 관찰 결과일 뿐 완료 허가가 아니다. 자동 `Completed`나 기록 정리는 하지 않는다. `NeedsRecovery` 스냅샷만으로 이전 제거 의도가 증명되지 않으면 보수적으로 모호함으로 남긴다.
- 검사 시점마다 새 파일 정보를 읽으며 세 위치를 하나의 원자적 스냅샷으로 고정하는 것은 아니다. 검사 결과를 재검사 없이 미래 파일 이동/삭제 권한으로 사용하면 안 된다. 현재 저널은 볼륨 일련번호만 증거로 저장하므로 GUID 기반 승인 계획 v2 검증도 아직 남아 있다.
- 기존 `RecoveryService`에 전송 저널을 주입했다. 전송 시도가 하나라도 있는 계획은 기존 두 위치 이름 변경 복구로 완료/실패를 자동 추론하거나 수동 기록 정리하지 않는다. 저널 조회 실패도 진행을 막는다. 앱 시작·복구 컨트롤러 모두 같은 저널을 사용한다. 저널 없는 기존 포트 테스트는 기존 동작을 유지한다.
- 현재 복구 화면에는 전송 기록의 별도 확인 필요와 기록 정리 차단만 표시한다. 상세 세 위치 결과를 화면에 연결하거나 자동 정리하는 기능은 아직 없다. 세 위치 검사는 백엔드 유스케이스에서 사용할 수 있다.

## 목표와 첫 지원 범위

사용자가 C:의 파일을 D:의 정리 위치로 이동하고, 같은 안전 경계로 되돌릴 수 있게 한다. 분류 규칙 v3 JSON, 노드 편집기, 미리보기 → 최종 확인 흐름은 바꾸지 않는다. 자동 감시는 계속 대기 등록만 한다.

첫 구현 범위는 로컬 NTFS 볼륨 사이의 일반 파일이다. 일반 파일의 주 데이터 스트림, 생성·수정 시각, 보존 가능한 기본 속성을 처리한다. 대상 폴더 권한을 상속하며 원본 ACL의 동일 복제를 보장하지 않는다. 명명된 추가 스트림(ADS), EFS 암호화, 여러 하드 링크, 재분석 지점·클라우드 플레이스홀더는 지원 검사에서 거부한다. 다른 파일 시스템·네트워크 공유·폴더 이동은 별도 지원 전까지 거부한다. 지원하지 않는 내용을 조용히 버린 뒤 원본을 삭제해서는 안 된다.

지원 범위는 파일을 변경하기 전에 검사하고, 이 제한을 오류 메시지와 README에 표시한다. 공간이 부족하면 실패하며, 남은 공간 사전 조회는 성공 보장이 아니다. 관리자 권한 상승이나 읽기 전용 속성 해제로 실패를 우회하지 않는다.

## 객체 동일성과 내용 동일성

- 원본이 승인받은 **그 파일**인지: 볼륨 ID·파일 ID·크기·수정 시각·SHA-256을 확인한다.
- 복사본이 승인받은 **그 내용**인지: 크기와 주 스트림 SHA-256을 확인한다. 허용한 메타데이터 보존도 별도로 확인한다.
- 임시·최종 복사본이 **앱이 생성한 파일**인지: 전송 시도에 기록한 볼륨 ID·파일 ID를 확인한다. 같은 해시나 파일명만으로 소유권을 추정하지 않는다.

다른 볼륨으로 복사하면 객체 ID가 달라진다. 되돌리기로 원래 경로에 새로 복사한 파일도 최초 원본 ID와 다르므로, 원본 계획 지문 대신 해당 역전송의 결과 지문으로 완료를 확인해야 한다.

## 역할 분리

승인·배치 실행을 맡는 조율자는 `IFileTransferOperations`와 `ITransferJournal` 같은 좁은 포트를 주입받는다. 이름은 구현 단계에서 확정한다. 하나의 거대한 자유 형식 `execute(command)`나 범용 삭제 포트를 만들지 않는다.

파일 작업 포트는 잠긴 원본 세션 열기, 앱 소유 임시 파일 생성, 제한된 복사·검증, 덮어쓰기 없는 확정, 검증된 세션 원본 제거를 제공한다. 원시 Windows 핸들은 인프라 구현 내부에 둔다. 원본 세션은 복사부터 제거까지 유지하고, 파일 지문·해시는 가능한 한 같은 핸들에서 읽는다. 작업 중 원본의 쓰기·이름 변경·삭제 공유를 허용하지 못하는 방식으로 열며, 이미 열린 다른 핸들과 충돌하면 이동을 거부한다. 부모 경로가 링크로 바뀌는 경쟁도 검증·디렉터리 핸들 보호로 막아야 한다.

파일 일꾼은 SQLite나 UI를 모르고, 기록 일꾼은 파일을 옮기지 않는다. 조율자만 기록 성공을 확인한 뒤 다음 파일 작업을 요청한다. 테스트에서는 파일 작업·기록 포트에 각각 실패를 주입할 수 있어야 한다.

## 단일 파일 전송 순서

아래 이름은 기존 `StepStatus`에 그대로 추가할 값이 아니라 전송 시도 내부의 단계다. 상위 단계는 전체 이동이 끝난 뒤에만 `Applied`가 된다.

1. `Prepared`: 계획 해시·승인·경로·지원 범위·원본 동일성을 검사한다. 실제 대상 볼륨을 확인하고 대상 폴더를 안전하게 준비한다.
2. `CopyIntent`: 시도 ID·방향·원본/최종/임시 경로를 DB에 먼저 기록한다. 임시 파일은 최종 목적지와 같은 폴더에서 충돌 없이 새로 생성한다. 생성 직후 객체 ID를 기록하기 전에는 복사를 시작하지 않는다.
3. `CopyVerified`: 잠긴 원본에서 제한된 버퍼로 복사한다. 임시 파일 데이터를 flush한 후 별도 읽기 검증으로 내용 해시를 확인한다. 메타데이터를 보존·검사하고 결과 지문을 기록한다. 기록 실패·원본 변경·복사 실패에는 원본을 남긴다.
4. `CommitIntent`: 임시 파일을 최종 이름으로 확정할 의도를 기록한다. 승인된 목적지가 생겼다면 다른 이름으로 즉석 재계획하지 않고 멈춘다.
5. `DestinationCommitted`: 임시 파일을 같은 볼륨 안에서 덮어쓰기 없이 이름 변경한다. 최종 파일의 ID·내용·메타데이터를 재검사하고 결과를 기록한다. 기록 실패에는 원본을 제거하지 않는다.
6. `SourceRemoveIntent`: 최종 파일이 온전하고 원본도 승인받은 파일인지 다시 확인한다. 필요한 핸들 보호를 유지한 채 원본 제거 의도를 먼저 기록한다.
7. `SourceRemoved`: 경로 문자열로 새로운 파일을 찾아 지우는 대신 검증한 원본 객체에 한정해 제거한다. 핸들 종료 후 원본 부재와 온전한 최종 파일을 확인한다. 원본이 남았거나 판정할 수 없다면 완료가 아니다.
8. `Completed`: 전송 완료·상위 단계 `Applied`·이벤트를 한 DB 트랜잭션에서 확정한다. 배치 전체 완료 뒤에만 성공 결과를 반환하고 대기 목록을 정리한다.

파일 시스템과 SQLite는 하나의 원자적 트랜잭션이 아니다. 각 작업은 먼저 의도를 저장하고 실제 결과를 뒤에 저장한다. 작업은 수행됐지만 결과 기록이 없는 구간을 복구 검사로 다룬다. Flush도 임의의 장치 고장·전원 장애에 대한 절대 보장이 아니며, 데이터 안전을 확인할 수 없을 때 성공 처리하지 않는다.

## 중단·실패 정책

원본 제거 전에는 검증된 원본을 남기는 것이 우선이다. 파일명 접두사만 맞는 임시 파일을 지우거나, 원본·복사본 해시가 같다는 이유만으로 둘 중 하나를 자동 삭제하지 않는다.

| 실제 위치·기록 | 재시작 처리 |
| --- | --- |
| 원본 온전, 임시 파일 없음, 복사 전 의도만 있음 | 파일 이동 없이 실패 기록을 정리할 수 있다. |
| 원본 온전, 앱 소유가 확인된 불완전 임시 파일 | 복사 미완료로 표시한다. 임시 파일 정리는 명시적 요청과 소유권·원본 재검사 후 수행한다. |
| 임시 파일은 있지만 생성 객체 ID가 기록되지 않음 | 앱 소유로 추정하지 않는다. 확인 필요로 둔다. |
| 원본 온전, 검증된 최종 파일도 있음 | 원본 제거 실패 또는 중단으로 표시한다. 둘 다 보존하고 완료·원본 삭제를 자동 실행하지 않는다. |
| 원본 없음, 기록된 앱 소유 최종 파일의 내용·ID 일치, 원본 제거 의도 있음 | 기록이 온전할 때 파일 작업 없이 완료 기록을 정리할 수 있다. |
| 원본 없음, 최종 파일 검증 실패 또는 제거 의도 없음 | 확인 필요. 성공으로 추정하지 않는다. |
| 볼륨이 분리됨·경로가 다른 장치로 바뀜·지문 불일치 | 확인 필요. 다른 장치의 같은 이름 파일을 대신 쓰지 않는다. |

배치의 앞선 이동이 완전히 완료되고 뒤 단계가 복사 전에 확실히 실패했다면 앞선 이동을 역순으로 보상할 수 있다. 최종 복사본이 생겼지만 원본 제거 여부가 불확실하거나 기록 저장에 실패했다면 자동 보상을 강행하지 않고 배치 전체를 `NeedsRecovery`로 멈춘다. 일부 파일의 이동·반환 기록은 숨기지 않는다. 이때 저장된 대기 목록은 유지하고 기존 승인은 재사용하지 않는다.

## 되돌리기

같은 볼륨 이동은 기존 덮어쓰기 없는 이름 변경을 유지한다. 다른 볼륨 이동은 완료된 최종 파일을 역전송의 원본으로 삼고, 최초 원본 경로를 목적지로 삼는다. 역전송도 임시 복사 → 검증 → 확정 → 검증된 전송 원본 제거를 그대로 따른다.

완료된 이동 결과의 객체 ID·내용이 바뀌었거나 원래 위치에 파일이 있으면 거부한다. 원래 위치에 동명이 있는 경우 Rename 정책으로 다른 곳에 돌려놓지 않는다. 공간 부족·볼륨 분리·역전송 원본 제거 실패에도 자동 덮어쓰기나 자동 삭제를 하지 않는다. 역전송 시도 기록을 정방향 기록과 분리하며, 새로운 결과 지문으로 `RolledBack`을 확인한다.

## 계획 서명과 SQLite 호환

- 기존 규칙 v3 JSON은 변경하지 않는다. 이동 방식은 파일·대상 볼륨으로 결정하는 실행 정보이지 분류 조건이 아니다.
- 기존 계획의 승인 해시 형식 v1은 그대로 검증한다. 신규 계획만 명시적인 계획 형식 v2를 사용한다. 기존 기록의 기본 버전은 1이다.
- v2 승인 대상에는 이동 방식(`RenameWithinVolume`/`CopyThenRemove`), 대상 볼륨 식별 정보와 보존 정책을 포함한다. 볼륨 정보는 드라이브 글자 비교가 아니라 실제 볼륨 조회로 얻는다. 없는 목적지에는 가장 가까운 안전한 기존 상위 폴더를 조회한다. 확정·원본 제거 전에도 대상 볼륨이 같은지 검사한다.
- `transfer_attempts` 같은 별도 기록에 시도 ID, 계획/단계 ID, 정방향·역방향, 단계, 세 경로, 임시/최종 객체 ID, 검증 결과·오류를 둔다. 실행 중 이 값들을 갱신해도 원본 승인 계획이나 해시는 변경하지 않는다.
- 기록의 각 단계 전이는 허용된 이전 상태에서만 트랜잭션으로 적용한다. 시도는 append-only로 보존하고, 재시도는 새 시도를 만들며 진행 중 시도를 덮어쓰지 않는다.
- 마이그레이션은 기존 이력·승인·해시를 보존하고 실패하면 파일 작업 전에 중단한다. 지원하지 않는 더 높은 DB 버전은 쓰지 않는다. 기존 v1 파일 ID만으로 다른 볼륨 복사 완료를 추정하지 않는다.

## 구현 순서와 활성화 조건

1. 파일의 객체 동일성/내용 동일성 계약, 전송 시도 자료형·상태 전이, 삭제 허용의 좁은 경계를 정의하고 순수 테스트를 만든다.
2. SQLite 버전별 마이그레이션·전송 저널·계획 해시 v1/v2 호환을 구현한다. 기존 DB 복사본과 신규 DB에서 테스트한다.
3. Windows 볼륨 조회·파일 세션·지원 범위 검사·임시 복사/검증을 구현한다. 이 단계에서는 원본 제거 없이 포트 테스트만 한다.
4. 단일 다른 볼륨 이동, 원본 제거, 역전송, 세 위치 복구를 연결하고 모든 기록 경계의 실패 테스트를 통과시킨다.
5. 배치 보상·대기 목록·감시 등록 흐름을 연결한다. 기존 같은 볼륨 테스트도 계속 통과해야 한다.
6. 임시 복사 파일만 사용하는 실제 두 로컬 NTFS 볼륨 테스트를 한다. 파일 내용·위치·기록·되돌리기를 확인하고 나서 지원을 활성화한다. 테스트 가상 포트만 통과한 상태는 실제 드라이브 지원 완료가 아니다.

필수 실패 시나리오: 디스크 용량 부족, 복사 중 읽기/쓰기 오류, 원본 잠금 실패·내용 변경, 임시/최종 이름 충돌, 각 DB 의도·결과 기록 실패, 복사/확정/원본 제거 직후 중단, 볼륨 분리, 앱 소유 파일 교체, 원본 제거 실패로 두 복사본이 남음, 역전송 목적지 충돌·용량 부족, 일부 배치 완료 후 복구 필요, 취소 요청. 취소는 원본 제거 전에는 원본을 유지하고, 제거 시작 뒤에는 결과 판정·기록까지 수행한 다음 다음 파일을 시작하지 않는 경계로 처리한다.

## Windows 근거

다른 볼륨의 `MOVEFILE_COPY_ALLOWED`는 복사·삭제로 구현되며, 원본 삭제에 실패해도 API 성공을 반환할 수 있다. 이 반환값만으로 NookBit의 이동 완료를 판단하지 않는다. 다른 볼륨 이동의 권한 상속 차이도 지원 범위에 반영한다. [Microsoft: MoveFileExW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw).

핸들의 읽기/쓰기/삭제 공유와 접근 권한은 Windows 계약에 맞게 정하며, 충돌 시 기존 파일을 강제로 조작하지 않는다. [Microsoft: CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew), [Microsoft: SetFileInformationByHandle](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-setfileinformationbyhandle). 데이터 flush는 명시적으로 확인한다. [Microsoft: FlushFileBuffers](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-flushfilebuffers).

최종 이름 확정은 `FileRenameInfo`의 `ReplaceIfExists=FALSE` 계약을 사용한다. [Microsoft: FILE_RENAME_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_rename_info).
