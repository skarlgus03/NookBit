# Cross-volume transfer design

상태: 전송 자료형·SQLite 기록, Windows 복사/검증·최종 확정·전송 원본 제거, 세 위치 복구 검사와 정방향/역방향 원자적 완료·승인 계획 v2 계약 기반을 구현했다. 2026-10-04 실제 C:/D: NTFS 볼륨에서 정상 왕복·양방향 충돌·부분 복사 재개·확정/제거 기록 복구의 6개 시나리오가 통과했다. [실행 결과와 남은 검증 범위](cross-volume-test-run.md)를 참고한다. 아래 각 구현 단계의 기존 단일 볼륨 테스트 설명은 해당 테스트의 범위이며 새 시험 결과와 구분한다. 이어 실제 테스트 프로세스를 복사 중·확정 직후·원본 제거 직후·완료 기록 직전에 강제 종료한 4개 시험도 새 프로세스 복구·되돌리기까지 통과했다. 2026-10-05 실제 규칙 미리보기부터 v2 승인·같은 볼륨/다른 볼륨 혼합 실행·되돌리기·확실한 충돌의 역순 보상 5개 시험도 통과했다. 전원 차단·SQLite 트랜잭션 내부 임의 시점 종료·추가 미해결 경계·복구 정리와 앱 정리 흐름 연결은 별도 과제다. 현재 앱 실행기는 같은 볼륨의 덮어쓰기 없는 이름 변경만 지원한다.

## 통합 실행 조립 계약

중단된 전체 혼합 작업의 [조회·명시적 복구 계약](interrupted-operation-recovery.md)을 구현했다. 조회는 파일/DB 변경 없이 개수·후보·차단 이유를 제공한다. 명시적 선택은 공유 잠금 아래 재검사·원자적 선택 감사·상태 복원 후 기존 실행기로 재개하거나 역순 복원한다. 실제 선택 처리 10개가 통과했다. 정방향의 개별 복구→전체 재개도 지원 경계 11개를 검증했다. 온전한 원본과 부분 임시 파일을 보존하는 되돌리기도 실제 6개 시험을 통과했다. 2026-10-06 실제 혼합 작업 강제 종료·새 프로세스 복구 7개도 통과했다. 보존 부분 임시 파일의 명시적 승인 정리도 실제 두 볼륨 13개를 통과했다. 정리 자체의 실제 강제 종료·새 프로세스 마무리와 미지원 복사 시작 전/부분 역전송의 무변경 차단 5개도 통과했다. 이 두 경계의 복구 실행은 지원하지 않는다. 다음 단계는 앱 연결이며 모든 사고 상황을 보장하지 않는다.

통합 백엔드에서만 `Planner(engine, appDataRoot, CrossVolumeDrafts::Allow)`를 구성한다. 이 정책은 다른 드라이브의 읽기 전용 초안만 허용한다. 미리보기·고정 저장·승인 재검증에는 실제 `ITransferVolumeInspector`를 제공하며, 실행기는 같은 포트와 `ITransferStepExecutor`·`IRollbackTransferStepExecutor`를 빌려 받는다. 단계 전략은 `PrepareTransferPlanUseCase`가 실제 GUID로 선택하고 v2 승인에 고정한다. `SafeExecutor`가 Rename과 VerifiedCopy를 하나의 승인 순서로 실행·되돌리며 UI는 이 선택을 담당하지 않는다.

다른 드라이브 v1 계획은 각 작업 경계의 `PlanSignature::validateMovementScope`로 차단한다. 기존 2인자 Planner와 앱 조립부는 기본 거부 정책을 유지한다. 구형 승인 바이트·규칙 JSON·DB 형식은 변경하지 않는다. 배치가 확실한 이름 변경 실패를 만나면 앞선 적용 단계를 역순 보상하고, 복사/기록 결과가 불확실하면 파일을 임의 정리하지 않고 NeedsRecovery로 중단한다. 혼합 배치 중단 뒤 전체 재개는 이번 정상/충돌 시험과 별개다.

## 현재 구현된 기반

- `include/nookbit/domain/transfer.hpp`: 전송 방향·단계·시도·갱신 요청. 객체 동일성 검사와 내용 동일성 검사를 분리한다.
- `include/nookbit/application/transfer_journal.hpp`: 파일 작업과 분리된 `ITransferJournal` 계약.
- `SqliteTransferJournal`: 예상 이전 단계 검사, 단계에 맞는 지문·오류 증거 검사, 스냅샷과 이벤트의 원자적 기록, 이벤트 재생으로 재시작 복원.
- Schema v2: `transfer_attempts`·`transfer_events`를 추가한다. 기존 계획·승인·해시 형식 v1은 변경하지 않는다. 실행 중인 단계에만 시도를 연결하고 미해결 시도의 중복 시작을 막는다.
- Schema v3: `plans.format_version`(기존 행은 1), `steps.movement_json`(기존 행은 NULL)을 추가한다. 승인 계획 형식 v2와 DB Schema v3는 서로 다른 버전이다.
- Schema v4: `transfer_events.recovery_completed`를 추가한다. 기존 이벤트의 기본값은 0이며 오류와 복구 완료 감사를 분리한다. 승인 계획 형식과 규칙 JSON은 변경하지 않는다.
- Schema v5: `transfer_events.staging_cleanup`(기본 0)을 추가한다. 정리 없음/의도 기록/제거 결과를 이동 상태와 분리해 재생하며 기존 이벤트·해시를 보존한다.
- Schema v6: `transfer_events.recovery_removal_intent`(기본 0)을 추가한다. 중단된 확정 전송의 명시적 원본 제거 의도를 기록한다. 기존 이벤트에는 제거 권한을 부여하지 않으며 규칙 JSON·승인 계획·기존 해시는 유지한다.
- Schema v7: `transfer_events.copy_resume`(기본 0)을 추가한다. 부분 복사의 재개 의도·전체 검증 증거를 기존 실패 상태와 분리한다. 기존 기록에 이어쓰기 의도나 검증 결과를 부여하지 않는다.
- Schema v8: `transfer_events.staging_commit`(기본 0)을 추가한다. 전체 검증된 재개 복사본의 확정 의도·결과를 기록하고, 일반 실패 단계 재실행과 구분한다. 기존 승인·규칙 형식은 유지하며 이전 사건에 확정 권한을 부여하지 않는다.
- SQLite 이행: 버전순 마이그레이션, 실패 시 해당 이행 롤백, 지원 버전보다 높은 DB의 쓰기 거부.
- `transfer_journal_tests.cpp`: 정상 단계 전이, 잘못된 순서·증거·중복·낡은 갱신 거부, 정방향/역방향 별도 기록, 재시작 복원, 이벤트 저장 실패 원자성, 이전 DB·해시 보존, 이행 실패/재시도·더 높은 버전 거부를 검사한다.

`StagingCreated`는 임시 파일 생성 후 객체 ID를 기록하는 별도 단계다. 저널의 일반 `advance`는 호출자가 보고한 단계만 저장하며 파일 작업의 성공을 자체 보증하지 않는다. 원본 제거 유스케이스는 실제 제거 결과까지 확인한 뒤 별도 `completeForward`/`completeRollback`으로 전송·상위 단계·필요한 계획 완료를 원자적으로 기록한다. v2 혼합 배치·보상, 명시적 완료 기록 복구·확정 전송 마무리·검증된 임시 정리·부분 복사 이어쓰기를 백엔드에 연결했다. 전체 검증된 재개 복사본의 최종 확정까지 별도 백엔드로 연결했다. 확정 결과 미기록 복구도 별도 백엔드로 연결했다. 완료된 되돌리기의 기록된 부분 임시 파일 정리는 별도 승인 경로로 제공한다. 앱 흐름 연결과 소유 증거 없는 미기록 파일 정리는 아직 남아 있다.

### 승인 계획 v2의 현재 범위

`PrepareTransferPlanUseCase`는 복사 기능이 아닌 `ITransferVolumeInspector`만 빌려 사용한다. 서명되지 않은 Draft의 양쪽 볼륨을 조회하고 GUID가 같으면 `Rename`, 다르면 `VerifiedCopy`를 고정한다. 각 단계에 원본/목적지의 일련번호·GUID·NTFS와 `LocalNtfsBasic` 보존 정책을 담는다. 별도 `verify`는 현재 볼륨을 다시 조회해 교체·조회 불가를 거부한다. 승인 해시를 검증하는 기능이나 파일 핸들 잠금의 대체 기능은 아니므로 실행 직전과 보호된 파일 세션 안에서도 재검사가 필요하다.

`PlanSignature`는 v1의 바이트 형식을 그대로 유지하며 v2에서는 계약의 모든 필드를 포함한다. 모르는 버전·계약 누락·v1에 덧붙인 미서명 계약·잘못된 GUID/일련번호·일관되지 않은 전략은 거부한다. SQLite는 계획을 저장/복원할 때 형식을 검사하며 누락된 계약이나 알 수 없는 enum을 v1으로 해석하지 않는다.

`CreatePreviewUseCase`에 선택적으로 `ITransferVolumeInspector`를 주입하면 Planner의 초안을 v2로 준비한다. Freeze는 초안의 현재 볼륨을 확인하고, 재생성한 현재 초안도 v2로 준비한 뒤 전체 내용이 같을 때만 저장한다. Verify는 DB 서명·현재 볼륨·설정·규칙·다시 생성한 파일 계획을 모두 확인한 뒤 승인을 허용한다. 볼륨 조회 포트 없이 v2를 저장·승인할 수 없다. 기존 v1 흐름은 그대로 지원한다.

`SafeExecutor`에 읽기 전용 볼륨 포트를 주입하면 v2의 `Rename`을 실행·되돌리기·배치 보상할 수 있다. 배치 시작과 각 단계 의도 기록 직후, 되돌리기 시작과 각 역이동 직전에 계약을 재검증한다. 의도 이후 볼륨 교체에는 파일을 옮기지 않고 복구 필요로 멈춘다.

`ITransferStepExecutor`를 주입하면 v2 `VerifiedCopy` 계획도 실행할 수 있고, 복사가 포함된 다중/혼합 배치에는 역전송 포트도 필요하다. 기존 작업 잠금·승인 재검증·경로/원본 검사·계획과 단계 의도 기록 뒤 별도 `ExecuteTransferStepUseCase`를 호출한다. 이 유스케이스는 DB의 서명과 실행 의도를 다시 확인한 뒤 승인 계약을 복사/제거 포트에 전달한다. Windows 어댑터는 보호된 원본·목적지 부모/파일 핸들의 실제 GUID·일련번호·NTFS가 계약과 같은지 확인한다. 복사는 임시 생성 전에, 제거는 제거 의도 저장 전에 이 검사가 끝나야 한다. 부모와 파일 핸들은 이후 복사/확정 또는 검증/제거 동안 유지된다.

복사 단계는 완료 트랜잭션 후 DB의 Applied 기록·서명을 다시 확인한 뒤 다음 단계로 진행한다. 마지막 복사가 전체 계획도 완료했다면 완료 이벤트를 중복 저장하지 않는다. 복사 결과를 이름 변경으로 대체하지 않으며, 전송 오류의 확정 여부가 불확실하면 앞선 완료 파일까지 자동 보상하지 않고 복구 필요로 멈춘다.

`IRollbackTransferStepExecutor`를 주입하면 완료된 v2 복사/혼합 배치도 작업 잠금 안에서 되돌릴 수 있다. 전체 완료 파일을 읽기 전용으로 먼저 점검하고 역순으로 실행한다. 복사 결과는 `verifyRollback`으로 최종 객체 지문·충돌·현재 볼륨·정방향 증거를 확인하고, 이름 변경 결과는 기존 객체 지문 검사를 사용한다. 실제 역전송/역이동 직전에도 다시 검사한다. 사전 거부에는 다른 파일도 되돌리지 않는다. 의도 이후 실패에는 남은 파일과 전송 증거를 보존하고 복구 필요로 멈춘다. 이미 RolledBack인 단계는 복구 필요로 덮어쓰지 않는다.

뒤 단계의 의도 저장 실패 또는 실제 작업 전 원본 변경처럼 확실한 실패에는 앞선 완료 파일들을 같은 역순 절차로 보상한다. 복사/확정/제거 오류는 보수적으로 불확실한 실패로 취급하여 자동 보상을 강행하지 않는다. 성공한 보상 이후 계획은 Failed이고, 각 반환된 단계와 별도 역전송 결과는 RolledBack/Completed로 남는다. 마지막 역전송이 계획 완료를 원자적으로 기록했다면 완료 이벤트를 중복 추가하지 않는다.

앱 조립부에는 아직 볼륨/전송 포트를 연결하지 않아 앱은 v1을 생성하고 Planner도 드라이브 문자가 다른 경로를 거부한다. 혼합 배치는 논리적 두 볼륨·실제 임시 파일·SQLite로 검증했다. 실제 두 볼륨 왕복과 명시적 복구 정리를 검증한 뒤 앱 흐름을 활성화해야 한다. 기존 두 위치 복구는 v2를 자동 정리하지 않는다. 이름 변경 방식의 직전 조회→운영체제 이동 사이 경쟁 구간은 그대로 남아 있으며 Rename 경로까지 보호된 핸들 방식으로 바꾼 것은 아니다.

### 임시 복사 일꾼의 현재 범위

- `application/staged_copy.hpp`의 포트와 `WindowsStagedCopy` 어댑터를 추가했다. SQLite·UI를 모르며 원본 삭제 API를 제공하지 않는다. 검증된 세션만 임시 파일을 같은 부모의 최종 이름으로 확정할 수 있다. 아직 앱 실행기에 연결하지 않았다.
- 볼륨 조회와 계획 준비는 없는 경로의 가까운 기존 조상에서 일련번호·볼륨 GUID·파일 시스템을 읽고 폴더를 만들지 않는다. 기존 `open`은 없는 부모를 거부하고, 승인 계약을 받는 `openApproved`만 목적지 부모를 생성한다. 잠금 불가·경로 접근 불가도 실패다.
- `CopyIntent` 저장 성공과 원본 객체·전체 해시·승인 볼륨 검증 뒤 목적지 조상을 한 단계씩 연다. 각 조상의 로컬 고정 NTFS·승인 GUID/일련번호·일반 디렉터리 여부를 확인하고 보호 핸들을 유지한 채 다음 폴더를 만든다. 링크/마운트·기존 파일·장치 예약 이름·우회 경로를 거부한다. 실패·취소로 생긴 빈 폴더는 소유권을 추정해 자동 삭제하지 않는다.
- 부모는 `FILE_LIST_DIRECTORY | FILE_READ_ATTRIBUTES`와 읽기 공유만으로 연다. 속성 조회 전용 접근은 공유 잠금 검사에서 예외이므로 디렉터리 읽기 권한도 요구한다. 세션 동안 부모 이름 변경 및 재분석 변경에 필요한 쓰기 핸들을 차단한다. 근거: [CreateFile 공유 규칙](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilea).
- `open`은 원본 객체 ID·크기·수정 시각·SHA-256과 지원 범위를 검사하고 `CREATE_NEW`로 빈 임시 파일을 만든다. 호출자는 반환된 `createdFingerprint`를 `StagingCreated`로 저장한 뒤 `copyAndVerify`를 호출해야 한다. 기록 실패 시 복사를 진행하지 않는다.
- 복사는 1MiB 버퍼로 한 번만 수행하며 flush 후 임시 파일을 다시 읽어 해시를 계산한다. 원본도 다시 검증하고 생성/수정 시각·기본 속성을 보존·검사한다. 대상 ACL은 대상 폴더에서 상속한다.
- 실패·취소·세션 해제 시 원본이나 임시 파일을 자동 삭제하지 않는다. 빈 파일 생성 뒤 지문 조회가 실패한 경우도 파일명으로 소유권을 추정하지 않는다. 향후 저널 기반 복구가 다뤄야 한다.
- 현재는 고정 로컬 NTFS의 일반 단일 링크 파일만 받는다. ADS·EFS·재분석 지점·오프라인/회수 속성·압축·희소 파일·부모 재분석 지점(폴더 마운트 포함)은 거부한다. 압축/희소 처리와 제거 권한은 별도 설계 전까지 제공하지 않는다.
- 이번 실제 파일 테스트는 한 볼륨의 임시 폴더에서 복사·확정 원시 작업과 DB 경계 연동을 검사했다. 두 드라이브 전송 완료·공간 부족·실제 읽기/쓰기 장애·볼륨 분리는 아직 검증하지 않았다.

### 복사본 확정과 기록 연결

`CommitTransferCopyUseCase`는 외부에서 주입받은 복사·저널 포트로 `Prepared → CopyIntent → StagingCreated → CopyVerified → CommitIntent → DestinationCommitted`를 수행한다. 파일 일꾼끼리 직접 호출하거나 SQLite를 파일 일꾼 내부에서 사용하는 구조는 아니다. 승인·경로 정책·계획 서명 v2 검증을 대체하는 진입점이 아니며, 실제 앱 흐름에서는 아직 호출하지 않는다.

- 모든 파일 작업은 앞선 의도/증거 저장 성공 뒤에만 수행한다. 생성 지문 기록 실패에는 복사를 시작하지 않고, 확정 의도 기록 실패에는 이름을 바꾸지 않는다.
- 세션의 `commitNoReplace`는 복사 검증 성공 후 한 번만 허용한다. 원본·임시 파일 내용과 기본 메타데이터를 재검사하고 보유한 임시 파일 핸들의 `NtSetInformationFile(FileRenameInformation)`로 같은 부모 안에서만 이름을 바꾼다. 단순 파일명과 NULL 루트를 사용해 보호된 부모를 쓰기 접근으로 다시 열지 않는다. `ReplaceIfExists=FALSE`이며 최종 경로의 기존 파일을 덮어쓰지 않는다. API를 사용할 수 없으면 보호를 완화하지 않고 실패한다. 확정 후 flush와 객체·내용·메타데이터를 재검사한다. 근거: [FILE_RENAME_INFORMATION의 같은 디렉터리 이름 변경](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/ns-ntifs-_file_rename_information).
- Windows `DELETE` 접근 권한은 임시 파일 핸들의 이름 변경에 필요해 그 핸들에만 부여한다. 원본 핸들에는 부여하지 않으며 파일 제거/삭제 예약 API는 사용하지 않는다. 이 접근 권한과 프로그램의 원본 삭제 허가는 다른 개념이다.
- 읽기 전용·숨김 원본의 테스트에서 NTFS 이름 변경이 보관 속성을 추가하는 것을 확인했다. 확정 뒤 보존할 기본 메타데이터를 재적용하고 검사하여 이 변경도 처리한다. 재적용 실패는 원본을 유지한 채 복구 필요로 남긴다.
- 취소는 확정 의도 기록 전까지만 반영한다. 확정 의도 기록 뒤에는 결과 판정과 기록을 끝내고, 불확실한 결과를 단순 취소로 숨기지 않는다.
- 생성 실패는 생성 뒤 지문 조회 실패일 수도 있어 보수적으로 `NeedsRecovery`로 남긴다. 복사 실패/취소는 `Failed`/`Cancelled`로 기록하고 원본·부분 복사본을 보존한다. 기록 실패·확정 오류·확정 후 결과 저장 실패는 `NeedsRecovery`를 시도한다. 복구 필요 기록도 실패하면 오류를 반환하며 마지막 미해결 단계가 재시도를 막는다.
- 성공 반환은 `DestinationCommitted`이지 `Completed`가 아니다. 원본은 그대로 있고 상위 `StepStatus`·계획은 실행 중이다. 이 유스케이스 종료 시 핸들은 닫히며 원본 제거 단계로 자동 이어지지 않는다. 향후 전체 전송 조율에서는 검증부터 원본 제거까지 세션 수명·권한을 별도로 통합해야 한다.
- `commit_transfer_copy_tests.cpp`는 실제 SQLite 재열기와 임시 NTFS 파일로 정상 확정, 각 저장 경계의 실패, 지속적인 DB 쓰기 실패, 확정 직후 API 오류 주입, 이름 충돌, 취소, 중복/미해결 시도 거부와 원본 보존을 검사한다. OS 강제 종료·전원 차단·두 볼륨의 전체 전송 시험은 아니다.

## 정방향 원본 제거와 완료

`FinalizeTransferUseCase`는 `DestinationCommitted`의 정방향 시도만 처리한다. 다시 읽은 계획 서명·원본 지문·출발/도착 경로와 실행 상태를 검사하고 `ITransferSourceRemoval`의 보호 세션을 연다. 이 유스케이스와 제거 일꾼은 실제 앱 정리 버튼에 등록하지 않았다.

1. 원본·최종 파일과 부모 경로를 보호하고 두 파일의 객체 ID·크기·SHA-256·수정 시각을 재검증한다. 임시 경로도 실제로 비어 있어야 한다.
2. `SourceRemoveIntent` 저장이 성공한 뒤에만 제거 함수를 호출한다. 저장 실패와 그 이후 복구 기록 실패에도 제거를 실행하지 않는다.
3. 제거 직전 같은 핸들로 다시 검증한다. 원본 핸들에 `FileDispositionInfo`로 제거를 요청하고 닫기 성공·정확한 원본 경로의 부재·보호된 최종 복사본을 확인한다. 일반 임의 경로 삭제나 재귀 삭제 API는 없다.
4. `SourceRemoved`를 저장하고 `completeForward`로 전송 `Completed`·단계 `Applied`·이력 이벤트를 한 트랜잭션에 기록한다. 모든 단계가 적용/건너뜀이고 미해결 전송이 없을 때만 계획 `Completed`도 같은 트랜잭션에 저장한다. 아직 남은 단계가 있으면 계획은 실행 중이다. 승인 계획의 원본 지문은 덮어쓰지 않는다.

- 복사 세션과 제거 세션은 분리되어 있다. 그 사이 파일이 바뀔 수 있으므로 제거 세션을 새로 열고 원본·최종 객체와 내용을 다시 검증한다. 제거 의도부터 제거·완료 기록까지는 같은 보호 세션을 유지한다.
- 원본은 읽기/제거 접근, 최종 파일은 읽기 접근만 요청하고 파일 공유는 허용하지 않는다. 다른 프로세스의 기존 핸들과 충돌하거나 필요한 권한이 없으면 제거하지 않는다. ADS·다중 링크·재분석 지점 등 기존 지원 검사도 다시 적용한다.
- 읽기 전용 원본은 속성을 강제로 바꾸지 않고 두 파일을 남겨 복구 필요로 처리한다. 로컬 고정 NTFS 일반 파일의 좁은 제거 경계만 구현했다.
- 제거 의도 전 취소는 `DestinationCommitted`를 그대로 두고 두 파일을 보존한다. 제거 의도 뒤에는 취소 때문에 결과 판정·기록을 중단하지 않는다.
- 제거 전 실패는 원본·최종 파일을 보존한다. 제거 예약/닫기 이후 오류는 원본이 이미 사라졌을 수도 있다. 이때 두 파일 보존을 약속하지 않으며 최종 복사본을 삭제하거나 되돌리지 않고 복구 필요로 남긴다. 결과·완료 DB 기록 실패도 성공으로 반환하지 않는다.
- `completeForward`는 제거 결과 기록 이후만 허용하고 부모 실행 상태도 검사한다. 실제 SQLite 완료 이벤트 실패 테스트에서 전송/단계/계획 완료 전체가 롤백된다. 이후 복구 필요 기록도 실패하면 마지막 미해결 단계가 재실행을 막는다.
- 현재 한 볼륨의 테스트 전용 임시 파일로 실제 원본 제거와 실패 경계를 확인했다. 두 볼륨 전체 전송/역전송, 배치 보상, 전원 차단, 계획 서명 v2·볼륨 GUID 승인, 앱 진입점의 작업 잠금 통합은 활성화 전에 남은 작업이다. 영구 삭제 일반 허용 설정은 바꾸지 않았다.

## 읽기 전용 전송 복구 검사

`InspectTransferRecoveryUseCase`는 저널 시도 하나를 다시 읽고, 기존 계획 서명·단계 ID·정방향/역방향 경로·원본 내용 연결을 검증한 뒤 세 위치를 검사한다. 신뢰할 수 없는 계획은 임의 경로를 읽지 않고 `UntrustedRecord`로 반환한다. 저널 손상이나 읽기 실패는 오류로 반환한다. 파일 작업이나 전송/상위 상태 쓰기는 제공하지 않는다.

`WindowsTransferFileInspector`는 복사 일꾼과 별도의 포트 구현이며 읽기 전용 Windows 헬퍼만 공유한다. 안전한 기존 조상에서 볼륨을 확인하고 보호된 핸들로 객체·내용을 읽는다. 지원하지 않는 파일·부모 재분석 지점·쓰기 잠금·접근 불가를 `Unavailable`로 반환하며 폴더나 파일을 생성하지 않는다.

- 세 파일 상태: `Missing`, `Matches`, `ObjectOnly`(생성 ID만 일치하고 완전한 내용 검증 기록 없음), `Unowned`, `Changed`, `OtherVolume`, `Unavailable`.
- 같은 내용의 새 파일도 객체 ID가 다르면 `Unowned`다. 검증 전 임시 파일 이름만으로 소유권을 인정하지 않는다. 기록된 볼륨과 다른 위치나 분리된 드라이브를 원본 없음으로 취급하지 않는다.
- 결과: 복사본 미관찰, 미검증 임시 객체, 검증된 임시 복사본, 원본과 기록된 최종 복사본이 함께 남음, 최종 경로에 검증된 임시 객체가 있지만 확정 결과 기록 없음, 제거 의도 이후 원본 없음, 변경/소유권 불명, 모호함, 확인 불가, 기록 신뢰 불가. 각 결과에 설명과 관찰 오류를 제공한다.
- `SourceAbsentAfterRemoveIntent`도 관찰 결과일 뿐 완료 허가가 아니다. 자동 `Completed`나 기록 정리는 하지 않는다. `NeedsRecovery` 스냅샷만으로 이전 제거 의도가 증명되지 않으면 보수적으로 모호함으로 남긴다.
- 검사 시점마다 새 파일 정보를 읽으며 세 위치를 하나의 원자적 스냅샷으로 고정하는 것은 아니다. 검사 결과를 재검사 없이 미래 파일 이동/삭제 권한으로 사용하면 안 된다. 현재 저널은 볼륨 일련번호만 증거로 저장하므로 GUID 기반 승인 계획 v2 검증도 아직 남아 있다.
- 기존 `RecoveryService`에 전송 저널을 주입했다. 전송 시도가 하나라도 있는 계획은 기존 두 위치 이름 변경 복구로 완료/실패를 자동 추론하거나 수동 기록 정리하지 않는다. 저널 조회 실패도 진행을 막는다. 앱 시작·복구 컨트롤러 모두 같은 저널을 사용한다. 저널 없는 기존 포트 테스트는 기존 동작을 유지한다.
- 현재 복구 화면에는 전송 기록의 별도 확인 필요와 기록 정리 차단만 표시한다. 상세 세 위치 결과를 화면에 연결하거나 자동 정리하는 기능은 아직 없다. 세 위치 검사는 백엔드 유스케이스에서 사용할 수 있다.

## 목표와 첫 지원 범위

사용자가 C:의 파일을 D:의 정리 위치로 이동하고, 같은 안전 경계로 되돌릴 수 있게 한다. 분류 규칙 v3 JSON, 노드 편집기, 미리보기 → 최종 확인 흐름은 바꾸지 않는다. 자동 감시는 계속 대기 등록만 한다.

첫 구현 범위는 로컬 NTFS 볼륨 사이의 일반 파일이다. 일반 파일의 주 데이터 스트림, 생성·수정 시각, 보존 가능한 기본 속성을 처리한다. 대상 폴더 권한을 상속하며 원본 ACL의 동일 복제를 보장하지 않는다. 명명된 추가 스트림(ADS), EFS 암호화, 여러 하드 링크, 재분석 지점·클라우드 플레이스홀더는 지원 검사에서 거부한다. 다른 파일 시스템·네트워크 공유·폴더 이동은 별도 지원 전까지 거부한다. 지원하지 않는 내용을 조용히 버린 뒤 원본을 삭제해서는 안 된다.

지원 범위는 파일을 변경하기 전에 검사하고, 이 제한을 오류 메시지와 README에 표시한다. 공간이 부족하면 실패하며, 남은 공간 사전 조회는 성공 보장이 아니다. 관리자 권한 상승이나 읽기 전용 속성 해제로 실패를 우회하지 않는다.

## 현재 코드에서 바꿔야 할 경계

| `SafetyInvariants::permanentDeleteAllowed` | 임의 삭제 금지는 유지한다. 검증된 이동 원본 제거와 앱 소유 임시 파일 정리만 좁은 계약으로 허용하는 의미를 별도로 표현한다. 단순히 이 값을 `true`로 바꾸지 않는다. |

## 객체 동일성과 내용 동일성

- 원본이 승인받은 **그 파일**인지: 볼륨 ID·파일 ID·크기·수정 시각·SHA-256을 확인한다.
- 복사본이 승인받은 **그 내용**인지: 크기와 주 스트림 SHA-256을 확인한다. 허용한 메타데이터 보존도 별도로 확인한다.
- 임시·최종 복사본이 **앱이 생성한 파일**인지: 전송 시도에 기록한 볼륨 ID·파일 ID를 확인한다. 같은 해시나 파일명만으로 소유권을 추정하지 않는다.

다른 볼륨으로 복사하면 객체 ID가 달라진다. 되돌리기로 원래 경로에 새로 복사한 파일도 최초 원본 ID와 다르므로, 원본 계획 지문 대신 해당 역전송의 결과 지문으로 완료를 확인해야 한다.

## 역할 분리

승인·배치 실행을 맡는 조율자는 `IFileTransferOperations`와 `ITransferJournal` 같은 좁은 포트를 주입받는다. 이름은 구현 단계에서 확정한다. 하나의 거대한 자유 형식 `execute(command)`나 범용 삭제 포트를 만들지 않는다.

파일 작업 포트는 잠긴 원본 세션 열기, 앱 소유 임시 파일 생성, 제한된 복사·검증, 덮어쓰기 없는 확정, 검증된 세션 원본 제거를 제공한다. 원시 Windows 핸들은 인프라 구현 내부에 둔다. 원본 세션은 복사부터 제거까지 유지하고, 파일 지문·해시는 가능한 한 같은 핸들에서 읽는다. 작업 중 원본의 쓰기·이름 변경·삭제 공유를 허용하지 못하는 방식으로 열며, 이미 열린 다른 핸들과 충돌하면 이동을 거부한다. 부모 경로가 링크로 바뀌는 경쟁도 검증·디렉터리 핸들 보호로 막아야 한다.

파일 일꾼은 SQLite나 UI를 모르고, 기록 일꾼은 파일을 옮기지 않는다. 조율자만 기록 성공을 확인한 뒤 다음 파일 작업을 요청한다. 테스트에서는 파일 작업·기록 포트에 각각 실패를 주입할 수 있어야 한다.

## 단일 파일 전송 순서

아래 이름은 기존 `StepStatus`에 그대로 추가할 값이 아니라 전송 시도 내부의 단계다. 상위 단계는 전체 이동이 끝난 뒤에만 `Applied`가 된다.

1. `Prepared`: 계획 해시·승인·경로·지원 범위·원본 동일성을 검사하고 실제 대상 볼륨을 조회한다. 폴더나 파일을 생성하지 않는다.
2. `CopyIntent`: 시도 ID·방향·원본/최종/임시 경로를 DB에 먼저 기록한다. 보호된 원본을 재검증한 뒤 승인된 목적지 부모를 안전하게 준비하고, 임시 파일을 최종 목적지와 같은 폴더에 충돌 없이 새로 생성한다. 생성 직후 객체 ID를 기록하기 전에는 복사를 시작하지 않는다.
3. `CopyVerified`: 잠긴 원본에서 제한된 버퍼로 복사한다. 임시 파일 데이터를 flush한 후 별도 읽기 검증으로 내용 해시를 확인한다. 메타데이터를 보존·검사하고 결과 지문을 기록한다. 기록 실패·원본 변경·복사 실패에는 원본을 남긴다.
4. `CommitIntent`: 임시 파일을 최종 이름으로 확정할 의도를 기록한다. 승인된 목적지가 생겼다면 다른 이름으로 즉석 재계획하지 않고 멈춘다.
5. `DestinationCommitted`: 임시 파일을 같은 볼륨 안에서 덮어쓰기 없이 이름 변경한다. 최종 파일의 ID·내용·메타데이터를 재검사하고 결과를 기록한다. 기록 실패에는 원본을 제거하지 않는다.
6. `SourceRemoveIntent`: 최종 파일이 온전하고 원본도 승인받은 파일인지 다시 확인한다. 필요한 핸들 보호를 유지한 채 원본 제거 의도를 먼저 기록한다.
7. `SourceRemoved`: 경로 문자열로 새로운 파일을 찾아 지우는 대신 검증한 원본 객체에 한정해 제거한다. 핸들 종료 후 원본 부재와 온전한 최종 파일을 확인한다. 원본이 남았거나 판정할 수 없다면 완료가 아니다.
8. `Completed`: 전송 완료·상위 단계 `Applied`·이벤트를 한 DB 트랜잭션에서 확정한다. 배치 전체 완료 뒤에만 성공 결과를 반환하고 대기 목록을 정리한다.

파일 시스템과 SQLite는 하나의 원자적 트랜잭션이 아니다. 각 작업은 먼저 의도를 저장하고 실제 결과를 뒤에 저장한다. 작업은 수행됐지만 결과 기록이 없는 구간을 복구 검사로 다룬다. Flush도 임의의 장치 고장·전원 장애에 대한 절대 보장이 아니며, 데이터 안전을 확인할 수 없을 때 성공 처리하지 않는다.

## 중단·실패 정책

원본 제거 전에는 검증된 원본을 남기는 것이 우선이다. 파일명 접두사만 맞는 임시 파일을 지우거나, 원본·복사본 해시가 같다는 이유만으로 둘 중 하나를 자동 삭제하지 않는다.

| 실제 위치·기록 | 재시작 처리 |
| --- | --- |
| 원본 온전, 임시 파일 없음, 복사 전 의도만 있음 | 파일 이동 없이 실패 기록을 정리할 수 있다. |
| 원본 온전, 앱 소유가 확인된 불완전 임시 파일 | 복사 미완료로 표시하고 보존한다. 현재 정리 구현은 전체 검증 해시가 기록된 복사본만 허용하며 부분 파일 정책은 미구현이다. |
| 임시 파일은 있지만 생성 객체 ID가 기록되지 않음 | 앱 소유로 추정하지 않는다. 확인 필요로 둔다. |
| 원본 온전, 검증된 최종 파일도 있음 | 원본 제거 실패 또는 중단으로 표시한다. 둘 다 보존하고 완료·원본 삭제를 자동 실행하지 않는다. |
| 원본 없음, 기록된 앱 소유 최종 파일의 내용·ID 일치, 원본 제거 의도 있음 | 기록이 온전할 때 파일 작업 없이 완료 기록을 정리할 수 있다. |
| 원본 없음, 최종 파일 검증 실패 또는 제거 의도 없음 | 확인 필요. 성공으로 추정하지 않는다. |
| 볼륨이 분리됨·경로가 다른 장치로 바뀜·지문 불일치 | 확인 필요. 다른 장치의 같은 이름 파일을 대신 쓰지 않는다. |

배치의 앞선 이동이 완전히 완료되고 뒤 단계가 복사 전에 확실히 실패했다면 앞선 이동을 역순으로 보상할 수 있다. 최종 복사본이 생겼지만 원본 제거 여부가 불확실하거나 기록 저장에 실패했다면 자동 보상을 강행하지 않고 배치 전체를 `NeedsRecovery`로 멈춘다. 일부 파일의 이동·반환 기록은 숨기지 않는다. 이때 저장된 대기 목록은 유지하고 기존 승인은 재사용하지 않는다.

## 명시적 완료 기록 복구

`TransferRecoveryService`는 실행·되돌리기와 같은 `OperationMutex`를 획득한 뒤 `ReconcileTransferRecoveryUseCase`를 호출한다. 유스케이스를 직접 사용할 때도 호출자가 같은 작업 잠금을 보유해야 한다. 시작 시 자동 복구하거나 승인 작업을 재실행하는 진입점이 아니다.

대상은 제거 의도가 저널 이벤트에 실제 기록된 `SourceRemoveIntent`·`SourceRemoved`·`NeedsRecovery` 시도뿐이다. 서명된 계획과 경로·내용·방향·실행/복구 상태를 검사한다. 역전송은 완료된 정방향 결과 하나의 최종 객체 ID·해시·수정 시각에 연결되어야 한다. v2는 원래 승인된 볼륨 계약을 사용하며 역방향에는 볼륨 역할만 뒤집는다.

`WindowsTransferRecoveryGuard`는 부모 이름 변경·재분석 경로를 차단하고, 로컬 고정 NTFS 및 승인 GUID/일련번호를 검사한다. 최종 일반 파일은 쓰기·삭제 공유 없이 읽기 핸들을 열어 DB 저장이 끝날 때까지 유지한다. 최종 객체 ID·전체 SHA-256·크기·수정 시각을 재검증한 뒤 원본과 임시 경로의 부재를 확인한다. 부재는 검사 시점 관찰이며 부모 핸들이 새 파일 생성을 영구 차단하는 것은 아니다. 새 파일을 발견하거나 접근 불가·볼륨 변경·객체 교체·지원 밖 파일 형태이면 아무 파일·기록도 바꾸지 않는다.

저널 `reconcileCompleted`는 같은 트랜잭션 안에서 예상 시도의 경로·증거·단계·오류와 승인 해시/승인 여부 및 실제 제거 의도를 재확인한다. `Completed` 복구 이벤트, 정방향 `Applied`/역방향 `RolledBack`, 상위 상태 이력과 별도 `transfer_recovery_completed` 감사 이벤트를 함께 저장한다. 기존 오류는 완료 시 해제하지만 이전 오류 이벤트는 보존한다. 이벤트 재생도 제거 의도 없는 복구 완료를 거부하며 일반 `advance`로 복구 단계 건너뛰기는 불가능하다.

다른 단계가 아직 끝나지 않았거나 다른 전송이 미해결이면 현재 단계의 완료만 복구하고 부모를 완료로 바꾸지 않는다. 부모가 이미 `NeedsRecovery`라면 미해결 형제의 상태도 그대로 유지한다. 반복 완료·낡은 예상값·SQL 이벤트 실패는 기록을 부분 갱신하지 않는다.

파일 생성·이동·삭제, 임시 파일 자동 정리, 원본이 남은 복사의 마무리, 복사 재개는 이 복구 기능에 포함하지 않는다. 앱 복구 화면과 추가 실제 두 볼륨 사고 상황 시험은 아직 남아 있다.

## 부분 임시 복사본의 명시적 이어쓰기

`ResumePartialCopyUseCase`와 `PartialCopyResumeService`는 기존 시스템 작업 잠금 안에서 중단된 임시 파일만 이어 쓰고 전체 검증 증거를 기록한다. 대상은 StagingCreated/Failed/Cancelled/NeedsRecovery이며 임시 객체 ID가 기록돼 있고 최종 지문이 없어야 한다. 완료된 이어쓰기·임시 정리 중·원본 제거 복구 중인 시도는 거부한다. 원래 단계·오류와 승인 해시는 유지하며 최종 확정이나 원본 삭제를 하지 않는다.

`WindowsStagedCopy::openResume`는 기존 부모만 보호하고 OPEN_EXISTING으로 원본·임시 파일을 연다. 폴더나 파일을 생성·절단하지 않는다. 일반 단일 링크 파일 지원 범위, 원본의 ID·전체 SHA-256·크기·수정 시각과 v2 승인 볼륨을 확인한다. 임시 객체가 기록된 ID와 같고 원본보다 크지 않아야 하며 최종 경로는 없어야 한다. 기존 임시 파일의 전 바이트를 원본 앞부분과 1MiB 버퍼 단위로 비교한다. 동일 보호 세션 동안 외부 쓰기·교체를 차단하며 불일치에는 아무 데이터도 쓰지 않는다.

조율자는 보호 세션 안에서 현재 승인·예상 시도를 확인하고 별도 이어쓰기 의도를 먼저 저장한다. 기존 의도로 재시도할 때도 현재 승인을 대조하고 감사 이력을 저장한다. 세션은 검증된 임시 크기 위치에서 읽기/쓰기를 시작하며 앞부분을 다시 쓰거나 잘라내지 않는다. 중간 취소·I/O 실패에는 원본과 부분 파일·의도를 남긴다. 다음 명시적 재시도는 늘어난 앞부분 전체를 다시 검증한다.

복사 후 flush·두 파일 전체 해시·동일 객체·기본 메타데이터를 기존 복사 세션으로 재검증한다. 검증 결과와 임시 지문 갱신은 SQLite에서 감사와 함께 원자적으로 저장한다. 결과 저장 실패 시 실제 파일은 완성됐더라도 검증 완료로 간주하지 않고, 재시작 후 전체 앞부분 검증·증거 저장을 다시 수행한다. 검증 완료 시 일반 단계 재실행은 허용하지 않는다. 별도 명시적 임시 정리는 전체 검증 증거를 이용할 수 있다.

이어쓰기 결과는 이동 완료가 아니다. 검증된 재개 복사본의 확정은 아래 별도 작업이 맡는다. 확정 결과 미기록 복구는 아래 별도 작업으로 제공한다. 미기록 파일 정리·추가 실제 두 볼륨 사고 상황/다른 지점의 강제 종료 시험과 화면 연결은 아직 남아 있다. 원본 전체와 기존 앞부분을 모두 읽어 안전성을 확인하므로 절약되는 것은 주로 다시 쓰는 양이며 무조건 빠른 재개를 보장하지 않는다.

## 전체 검증된 재개 복사본의 최종 확정

`CommitResumedStagingUseCase`는 `CopyResume::Verified`가 저장된 StagingCreated/Failed/Cancelled/NeedsRecovery 시도만 받는다. 임시 전체 지문이 승인 원본과 같은 내용이고 다른 객체이며, 최종 지문·임시 정리·원본 제거 감사가 없어야 한다. `ResumedStagingCommitService`는 다른 실행·복구와 동일한 시스템 잠금으로 직렬화한다. 직접 유스케이스를 호출할 때도 동일 잠금이 필요하다.

`IStagedCopy::openVerified`의 기본 구현은 미지원이며 새 파일 생성 API로 대체하지 않는다. Windows 구현은 기존 원본과 임시 파일·부모를 보호하고, 일반 파일 지원 범위·승인 볼륨·원본 전체 SHA-256·임시 객체 ID와 전 바이트·크기·수정 시각·최종 경로 부재를 다시 검사한다. 파일 생성·절단·이어쓰기·메타데이터 갱신을 하지 않으며 확정 전용 세션으로 기존 no-replace 확정 절차를 재사용한다.

SQLite `recordStagingCommit`은 예상 스냅샷 전체와 현재 승인·해시·상위 상태를 대조하고 `StagingCommit::IntentRecorded`를 먼저 저장한다. 기존 의도 재시도도 현재 승인을 대조하고 감사한다. 이후 같은 세션에서 최종 이름으로 변경하고, 최종 객체가 검증된 임시 객체와 같으며 내용·수정 시각이 일치할 때만 `StagingCommit::Committed`와 `DestinationCommitted` 증거·감사를 원자적으로 저장한다. 앞선 실패/취소 사건은 삭제하지 않고 일반 `advance`의 재실행 금지도 유지한다.

확정만으로 원본을 제거하거나 단계/계획을 완료하지 않는다. 성공한 시도는 아래 별도 원본 제거 마무리로 넘길 수 있으며, 그때만 Verified+Committed 계보를 허용한다. 정방향은 Applied, 역방향은 RolledBack으로 끝나며 미해결 형제를 조기 완료하지 않는다.

의도 전 취소는 두 파일을 그대로 보존한다. 의도 이후에는 이름 변경 결과·기록까지 판정한다. 이름 변경 전에 충돌이나 오류가 발생하면 두 파일과 의도를 남기고 재검증 후 명시적으로 재시도할 수 있다. 이름 변경은 성공했지만 API 결과나 SQL 결과 저장이 끊긴 경우 원본+최종 파일과 의도를 보존한다. 임시 파일을 다시 생성하거나 최종 이름을 덮어쓰거나 원본을 제거하지 않으며, 재실행도 거부한다. 읽기 전용 검사는 CommitNotRecorded로 진단하며, 아래 별도 명시적 복구 작업으로 해당 확정 증거만 기록할 수 있다.

추가 실제 두 볼륨 사고 상황/다른 지점의 강제 종료 시험과 화면 연결은 아직 없다. 규칙 JSON v3·승인 계획 v2 해시 형식은 변경하지 않는다.

## 확정 결과가 누락된 전송의 명시적 기록 복구

`ReconcileTransferCommitUseCase`와 `TransferCommitRecoveryService`는 파일 이름 변경을 다시 수행하지 않고 최종 확정 증거만 복구한다. 기존 시스템 작업 잠금으로 직렬화하며 직접 유스케이스 호출도 동일 잠금이 필요하다. 자동 재개·원본 제거·상위 완료는 하지 않는다.

일반 복사는 CopyResume None/확정 감사 없음의 CommitIntent 또는 NeedsRecovery이면서 실제 이전 CommitIntent 사건이 있어야 한다. 재개 복사는 CopyResume Verified/StagingCommit IntentRecorded이고 기존 중단 단계에 있어야 한다. 임시 객체·전체 해시가 기록돼 있고 최종 결과·정리·원본 제거·완료 감사가 없는 경우만 허용한다. 현재 상태 이름만으로 과거 의도를 추정하지 않으며, SQLite 이벤트 재생과 실제 의도 조회가 모두 확인되어야 한다.

`ITransferCommitRecoveryGuard`는 변경 API가 없는 별도 읽기 전용 계약이다. Windows 구현은 기존 원본과 최종 파일을 GENERIC_READ/FILE_SHARE_READ로 열어 외부 쓰기·교체·삭제를 차단하고 부모 핸들도 유지한다. 일반 단일 링크 지원 범위·승인 볼륨 GUID/일련번호·원본 ID/전체 해시/크기/시각·기록된 임시 객체와 최종 ID/내용/시각 일치·생성/수정 시각과 기본 속성 일치·임시 경로 부재를 검사한다. 메타데이터 불일치도 자동 수정하지 않고 거부한다. 원본 또는 최종 파일 소실·교체·변경·새 임시 점유는 기록 복구 근거가 아니다.

보호 세션을 저장까지 유지한 채 `SqliteTransferJournal::reconcileDestinationCommitted`가 예상 스냅샷 전체·현재 승인 해시/승인 여부·방향별 상위 상태·실제 의도를 재확인한다. DestinationCommitted·최종 지문·StagingCommit Committed와 `transfer_commit_recovered` 감사를 한 트랜잭션으로 추가한다. 일반 단계 재실행은 계속 금지하고 과거 실패 사건은 보존한다. 저장 실패/취소에는 파일과 기존 기록을 그대로 유지하며, 재시작 후 동일 검증으로 명시적 재시도할 수 있다.

기록 복구 성공은 이동 완료가 아니다. 원본과 최종 파일이 모두 남으며 별도 아래 마무리만 원본 제거를 요청할 수 있다. 정방향/역방향 모두 지원한다. 추가 다른 볼륨 사고 상황·다른 지점의 강제 종료 시험·화면 연결은 아직 남아 있다. Schema v8·규칙 JSON v3·승인 계획 v2 형식은 변경하지 않는다.

파일 시스템과 SQL을 원자적으로 묶는 것은 아니다. 임시 부재 관찰 뒤 같은 이름 새 파일이 생길 수 있으며 기록 복구가 그 파일의 정리 권한을 부여하지 않는다. 이후 원본 제거 작업은 두 객체·메타데이터·임시 부재를 다시 보호 검사하므로 새 점유나 변경이 있으면 삭제 없이 멈춘다.

## 원본이 남은 확정 전송의 명시적 마무리

`ResumeCommittedTransferUseCase`는 최종 객체 지문까지 기록된 `DestinationCommitted`·`SourceRemoveIntent`·`NeedsRecovery` 시도만 받는다. 전체 검증과 최종 확정이 모두 기록된 재개 복사본도 받는다. 부분 복사, 확정 결과 미기록, 완료/취소 시도나 임시 정리 중인 시도는 받지 않는다. 자동 재개가 아니며 호출자가 시도 ID로 명시적으로 요청한다. `CommittedTransferResumeService`는 기존 실행·되돌리기·복구와 같은 시스템 잠금으로 직렬화한다. 앱 화면에는 아직 연결하지 않았다.

서명·경로·방향·상위 상태·역전송 원본을 검증한 뒤 기존 원본 제거 포트로 두 파일과 부모를 보호한다. 원본/최종 객체 ID·전체 SHA-256·크기·수정 시각·기본 메타데이터·일반 파일 지원 범위·임시 경로 부재와 v2 승인 볼륨을 재검사한다. 원본 교체·변경, 최종 변경, 새 임시 파일, 잠금 불가·잘못된 승인에는 어느 파일도 제거하지 않는다.

보호 세션을 유지한 채 저널 `recordRecoveryRemovalIntent`가 예상 시도 전체와 현재 승인 해시·승인 여부·상위 상태를 다시 대조한다. 실패 단계와 진단은 그대로 두고 별도 의도 이벤트와 감사 이력을 원자적으로 저장한 뒤에만 같은 원본 핸들을 제거한다. 기존 의도로 재시도할 때도 현재 승인을 다시 검사하고 재시도 감사를 저장한다. 일반 `advance`로 실패 단계를 실행 상태로 되돌리는 기능은 아니다. 취소는 의도 전에는 두 파일을 보존하고 의도 후에는 결과 판정·기록을 끝낸다.

제거 실패에는 두 복사본과 의도가 남는다. 제거 후 완료 저장 실패에는 최종 파일과 의도가 남고, 재시작 후 원본/임시 부재·최종 동일성을 보호 세션에서 확인해 기존 `reconcileCompleted`로 기록만 마무리한다. 새 원본 위치 점유는 삭제하거나 완료로 추정하지 않는다. 정방향은 Applied, 역방향은 RolledBack으로 기록하며 미해결 형제가 있으면 배치 전체를 완료로 만들지 않는다.

최종 확정 결과 미기록은 별도 확정 기록 복구 유스케이스로 먼저 처리한다. 미기록 파일 정리와 추가 실제 두 볼륨 사고 상황/다른 지점의 강제 종료 시험은 아직 남아 있다. 부분 파일 이어쓰기는 별도 백엔드로 전체 검증 단계까지 제공한다.

## 검증된 임시 복사본의 명시적 정리

`StagingCleanupService`는 실행·복구와 같은 `OperationMutex` 안에서 `CleanupTransferStagingUseCase`를 호출한다. 유스케이스 직접 호출에는 같은 작업 잠금이 필요하다. 기존 완료 기록 복구와는 별도 작업이며 시작 시 자동으로 삭제하지 않는다. 두 작업은 서명·경로·방향·실행/복구 상태·역전송 원본을 검사하는 순수 공유 함수 `verifyTransferRecoveryBinding`을 사용한다.

대상은 `Failed`·`Cancelled`·`NeedsRecovery` 시도 중 임시 객체 ID와 전체 검증 해시가 기록되어 있고 최종 확정 지문이 없는 경우뿐이다. 원본과 임시 복사본의 내용이 승인 내용과 일치해야 한다. 부분 복사본이나 생성 기록만 있고 검증 해시가 없는 파일은 사용자 수정 여부를 구별할 수 없으므로 삭제하지 않는다. 이름 접두사·같은 내용만으로 다른 객체의 소유권을 추정하지 않는다.

`WindowsStagingCleanup`은 안전한 부모, 로컬 고정 NTFS 및 승인 볼륨을 확인한다. 원본은 쓰기/삭제 공유 없는 읽기 핸들로 보존하고 임시 파일만 독점 읽기+DELETE 핸들을 연다. 두 객체의 ID·SHA-256·크기·수정 시각과 일반 단일 링크 파일 지원 범위를 확인한다. 최종 경로가 있거나 읽기 전용 임시 파일이면 정리를 거부하며 속성은 강제로 바꾸지 않는다. 세션 생성·해제만으로 삭제를 예약하지 않는다.

저널 `recordStagingCleanup`은 예상 시도 전체와 현재 승인 해시·승인 여부·상위 실행/복구 상태를 대조한다. 정리 의도와 `transfer_staging_cleanup` 감사 이력을 원자적으로 기록한 뒤에만 제거를 요청한다. 제거 직전 다시 검사하고 경로 삭제가 아닌 `FileDispositionInfo`로 보유한 임시 객체만 제거·닫기·부재 확인한다. 이후 원본을 재검증하고 정리 결과를 원자적으로 기록한다. 전송 단계·기존 오류·단계/계획 상태·승인 해시는 변경하지 않으며 이동 완료나 기존 승인 재실행 허가가 아니다.

의도 저장 실패에는 파일을 삭제하지 않는다. 결과 저장 실패에는 의도가 남아 재시작 후 명시적으로 재시도할 수 있다. 이전 의도가 있고 임시 경로가 없으면 원본과 최종 경로를 다시 확인한 후 제거 결과 기록만 마무리한다. 새 임시 경로 점유·원본 변경·볼륨 변경에는 재삭제나 기록 완료를 거부한다. 기록된 객체가 그대로 남아 있다면 동일 검사 후 제거를 다시 요청할 수 있다.

검사에서 삭제·기록까지 파일 시스템과 DB 전체를 원자적으로 묶을 수는 없다. 부모 보호는 새 파일 생성을 영구 차단하지 않으므로 삭제 뒤 새 점유 파일이 생기면 확인 필요로 멈춘다. 완료된 되돌리기의 기록된 부분 임시 파일 정리와 실제 두 볼륨 13개 시험은 별도 승인 경로로 제공한다. 소유 증거 없는 미기록 파일 정리와 화면 연결은 아직 남아 있다. 목적지 부모 생성은 승인된 복사 세션에 구현했고 생성 폴더 자동 정리는 제공하지 않는다.

## 되돌리기

역전송 백엔드의 현재 진입점은 `RollbackTransferUseCase`다. 정방향 `Completed` 시도와 서명된 원래 계획을 읽고, 실제 이동 결과의 ID·내용·수정 시각과 원래 위치의 부재/볼륨을 먼저 확인한다. 사전 충돌·변경 거부에는 계획 상태도 바꾸지 않는다. 새 역전송 ID·임시 경로를 사용하며 정방향 기록을 재사용하지 않는다.

v2에서는 원래 승인 볼륨을 읽기 전용으로 재검증한 뒤 `MoveContract`의 원본/목적지 볼륨 역할만 뒤집어 승인 API로 전달한다. 복사와 제거 시 보호된 핸들의 실제 볼륨도 다시 검사한다. 승인 계획과 최초 지문·해시는 바꾸지 않으며, 역전송 원본은 완료된 정방향의 최종 객체 지문이다. `rollback(planId, stepId, ...)` 어댑터는 같은 계획/단계의 완료된 정방향 결과 하나만 선택하며 없거나 모호한 경우 거부한다.

계획 `RollingBack`·단계 `RollbackIntentRecorded` 이후 기존 복사/확정 유스케이스와 방향을 지원하는 제거/완료 유스케이스를 재사용한다. SQLite의 역전송 `begin`과 제거 직전 검증은 완료된 정방향의 최종 객체 지문에 원본을 연결한다. 원래 위치의 충돌에 Rename 정책을 적용하지 않는다. 도중 오류는 복구 필요와 실제 남은 파일을 보존하며 임의로 다른 위치로 돌려놓지 않는다.

`completeRollback`은 역전송 완료·단계 `RolledBack`·이력 이벤트를 원자적으로 기록한다. 모든 단계가 되돌림/건너뜀일 때만 계획도 `RolledBack`으로 바꾼다. 복원된 새 파일의 지문은 역전송 결과에 기록하고 최초 승인 지문은 바꾸지 않는다. SQL 저장 로직은 정방향과 공유하되 실행/단계/완료 상태는 방향별로 검사한다.

실제 임시 파일의 왕복, 사전/확정 직전 원래 위치 충돌, 이동 파일 변경/동일 내용의 다른 객체, 역전송 제거 의도 실패, 제거 후 완료 기록 실패, 실제 SQLite 되돌림 완료 이벤트 실패를 검사했다. 두 로컬 볼륨 왕복과 실제 앱 되돌리기 버튼 연결은 아직 검증하거나 활성화하지 않았다.

같은 볼륨 이동은 기존 덮어쓰기 없는 이름 변경을 유지한다. 다른 볼륨 이동은 완료된 최종 파일을 역전송의 원본으로 삼고, 최초 원본 경로를 목적지로 삼는다. 역전송도 임시 복사 → 검증 → 확정 → 검증된 전송 원본 제거를 그대로 따른다.

완료된 이동 결과의 객체 ID·내용이 바뀌었거나 원래 위치에 파일이 있으면 거부한다. 원래 위치에 동명이 있는 경우 Rename 정책으로 다른 곳에 돌려놓지 않는다. 공간 부족·볼륨 분리·역전송 원본 제거 실패에도 자동 덮어쓰기나 자동 삭제를 하지 않는다. 역전송 시도 기록을 정방향 기록과 분리하며, 새로운 결과 지문으로 `RolledBack`을 확인한다.

## 계획 서명과 SQLite 호환

- 기존 규칙 v3 JSON은 변경하지 않는다. 이동 방식은 파일·대상 볼륨으로 결정하는 실행 정보이지 분류 조건이 아니다.
- 기존 계획의 승인 해시 형식 v1은 그대로 검증한다. 신규 계획만 명시적인 계획 형식 v2를 사용한다. 기존 기록의 기본 버전은 1이다.
- v2 승인 대상에는 이동 방식(`Rename`/`VerifiedCopy`), 양쪽 볼륨 식별 정보와 보존 정책을 포함한다. 볼륨 정보는 드라이브 글자 비교가 아니라 실제 볼륨 조회로 얻는다. 없는 목적지에는 가장 가까운 안전한 기존 상위 폴더를 조회한다. 향후 실행 연결 시 확정·원본 제거 전에도 승인된 볼륨이 같은지 검사해야 한다.
- `transfer_attempts` 같은 별도 기록에 시도 ID, 계획/단계 ID, 정방향·역방향, 단계, 세 경로, 임시/최종 객체 ID, 검증 결과·오류를 둔다. 실행 중 이 값들을 갱신해도 원본 승인 계획이나 해시는 변경하지 않는다.
- 기록의 각 단계 전이는 허용된 이전 상태에서만 트랜잭션으로 적용한다. 시도는 append-only로 보존하고, 재시도는 새 시도를 만들며 진행 중 시도를 덮어쓰지 않는다.
- 마이그레이션은 기존 이력·승인·해시를 보존하고 실패하면 파일 작업 전에 중단한다. 지원하지 않는 더 높은 DB 버전은 쓰지 않는다. 기존 v1 파일 ID만으로 다른 볼륨 복사 완료를 추정하지 않는다.

## 구현 순서와 활성화 조건

1. 파일의 객체 동일성/내용 동일성 계약, 전송 시도 자료형·상태 전이, 삭제 허용의 좁은 경계를 정의하고 순수 테스트를 만든다.
2. SQLite 버전별 마이그레이션·전송 저널·계획 해시 v1/v2 호환을 구현한다. 기존 DB 복사본과 신규 DB에서 테스트한다.
3. Windows 볼륨 조회·파일 세션·지원 범위 검사·임시 복사/검증을 구현한다. 이 단계에서는 원본 제거 없이 포트 테스트만 한다.
4. 단일 다른 볼륨 이동, 원본 제거, 역전송, 세 위치 복구를 연결하고 모든 기록 경계의 실패 테스트를 통과시킨다.
5. 배치 보상·대기 목록·감시 등록 흐름을 연결한다. 기존 같은 볼륨 테스트도 계속 통과해야 한다.
6. 임시 복사 파일만 사용하는 실제 두 로컬 NTFS 볼륨 테스트를 한다. 파일 내용·위치·기록·되돌리기를 확인하고 나서 지원을 활성화한다. 테스트 가상 포트만 통과한 상태는 실제 드라이브 지원 완료가 아니다.

필수 실패 시나리오: 디스크 용량 부족, 복사 중 읽기/쓰기 오류, 원본 잠금 실패·내용 변경, 임시/최종 이름 충돌, 각 DB 의도·결과 기록 실패, 복사/확정/원본 제거 직후 중단, 볼륨 분리, 앱 소유 파일 교체, 원본 제거 실패로 두 복사본이 남음, 역전송 목적지 충돌·용량 부족, 일부 배치 완료 후 복구 필요, 취소 요청. 취소는 원본 제거 전에는 원본을 유지하고, 제거 시작 뒤에는 결과 판정·기록까지 수행한 다음 다음 파일을 시작하지 않는 경계로 처리한다.

## Windows 근거

다른 볼륨의 `MOVEFILE_COPY_ALLOWED`는 복사·삭제로 구현되며, 원본 삭제에 실패해도 API 성공을 반환할 수 있다. 이 반환값만으로 NookBit의 이동 완료를 판단하지 않는다. 다른 볼륨 이동의 권한 상속 차이도 지원 범위에 반영한다. [Microsoft: MoveFileExW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw).

핸들의 읽기/쓰기/삭제 공유와 접근 권한은 Windows 계약에 맞게 정하며, 충돌 시 기존 파일을 강제로 조작하지 않는다. [Microsoft: CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew), [Microsoft: SetFileInformationByHandle](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-setfileinformationbyhandle). 데이터 flush는 명시적으로 확인한다. [Microsoft: FlushFileBuffers](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-flushfilebuffers).

최종 이름 확정은 `FileRenameInfo`의 `ReplaceIfExists=FALSE` 계약을 사용한다. [Microsoft: FILE_RENAME_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_rename_info).

보호된 원본 제거에는 `FileDispositionInfo`를 사용하며 닫기와 실제 부재를 별도로 확인한다. [Microsoft: FILE_DISPOSITION_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_disposition_info), [Microsoft: CloseHandle](https://learn.microsoft.com/en-us/windows/win32/api/handleapi/nf-handleapi-closehandle).
