# Same-volume metadata rename (first implementation)

## 적용 범위

새로 정리 준비하는 v2 초안의 모든 단계가 실제 GUID 기준 같은 볼륨 Rename이면 앱 조립부가 MetadataRename으로 고정한다. 다른 볼륨 또는 혼합 작업, 기존 고정/승인 계획은 기존 내용 해시와 보상 정책을 유지한다. C:→D: 큰 파일의 사전 전체 검사는 이번 변경으로 줄어들지 않는다.

이 정책은 파일 ID·볼륨·크기·수정 시각을 승인한다. 내용 해시 승인과 동일한 보장이 아니다. 확인 전 같은 객체의 내용을 바꾸면서 크기와 수정 시각도 원래대로 맞춘 변경은 검출하지 못한다. 보호된 원본 핸들을 유지하는 이동 호출 동안에는 외부 쓰기·교체·삭제를 차단한다. 목적지 덮어쓰기는 허용하지 않는다.

## 승인과 저장 계약

- MoveStrategy 값 0=Rename, 1=VerifiedCopy는 변경하지 않고 2=MetadataRename을 추가한다. 이 값은 기존 v2 승인 바이트에 이미 포함되는 이동 전략 필드에 서명된다. 기존 계획 해시와 JSON 규칙 v3는 변경하지 않는다.
- MetadataRename은 같은 승인 볼륨, 파일 ID, 내용 해시 없음이 필수다. 이번 구현은 복사/구형 Rename과 섞인 계획을 거부한다. 알 수 없는 enum은 계속 거부한다.
- SQLite schema v8의 기존 movement_json 및 error_code/error_detail을 사용한다. 이전 바이너리는 값 2를 읽거나 승인할 수 없으며 안전하게 거부한다. 새 바이너리는 구형 v1/v2 계획을 그대로 처리한다.
- 고정 때 규칙·목적지·파일 메타데이터를 재검사하지만 전체 내용은 읽지 않는다. 승인/실행 때 서명·설정·규칙·선택 경로를 확인하고, 개별 객체/접근 검사는 이동 시도에서 수행한다. 승인 없는 실행은 여전히 거부한다.

## 개별 실행과 실패

각 단계는 의도 기록 → 경로/실제 볼륨 검사 → 보호된 원본 핸들에서 객체·크기·수정 시각 검사 → 덮어쓰기 없는 핸들 기반 이름 변경 → 두 경로의 메타데이터 결과 검사 → 완료 기록 순서로 진행한다. 두 경로의 부모를 삭제/교체로부터 보호하고 재분석 지점·다른 볼륨·ADS·다중 링크를 거부한다. 접근/잠금은 실제 Windows 요청의 실패로 반환한다.

목적지 부모 폴더가 없으면 생성할 수 있다. 뒤에서 이동이 실패해도 생성한 빈 폴더를 자동으로 삭제하지 않는다.

확실한 실패는 Failed와 오류 코드/내용을 감사 사건과 한 트랜잭션에 저장한 뒤 다음 파일을 처리한다. 앞선 성공을 자동으로 되돌리지 않는다. 일부 실패한 작업은 상위 Failed로 끝내고 실제 Applied 파일만 대기 목록에서 제거한다. 실패 항목은 남기며 마지막/기록 되돌리기는 성공한 부분만 복원한다. 복원에도 내용 전체 검사는 하지 않는다.

이름 변경 결과가 불확실하거나 의도/완료/실패 감사 저장이 실패하면 NeedsRecovery로 멈추고 이후 파일을 시작하지 않는다. 원본/목적지·기록을 보존한다. 성공한 부분의 자동 보상이나 임의 기록 확정은 하지 않는다.

## 현재 제한과 검증

새 MetadataRename의 강제종료/불확실한 중단 후 전체 재개·되돌리기는 아직 지원하지 않는다. 시작 검사에서 명시적으로 차단·안내하며 파일 내용을 읽거나 기록을 자동 변경하지 않는다. 정상 완료/부분 실패 후 명시적 성공 부분 되돌리기는 지원한다. 구형 내용 해시 기반 중단 복구는 기존대로 유지한다.

자동 19/19 및 기존 실제 두 볼륨 비동기 경로 회귀가 통과했다. 새 실행기 시험은 성공·잠금·충돌·파일 변경·누락·의도 저장 실패·실패 감사 실패·이동 완료 감사 실패를 검사한다. 파일 전체 해시를 호출하면 실패시키는 대역으로 고정/승인/이동/되돌리기 내용 읽기 0회를 확인한다. 실패 감사 트랜잭션 실패 시 오류 상세와 상태가 함께 롤백되는지도 검사한다. 컨트롤러 시험은 성공 부분만 대기 목록에서 제거하고 부분 되돌리기가 가능한지 확인한다.

4 GiB 희소 시험 파일의 고정·승인·이동·되돌리기는 210 ms, 내용 해시 호출 0회였다. 희소 파일은 실제 4 GiB 데이터 파일의 디스크 처리량 시험이 아니며 사용자 환경의 실행 시간을 보장하지 않는다. 실제 복사 및 전원 손실 내구성 시험과 구분한다. 이 자료는 시험이 생성한 파일에만 적용했고 사용자 원본은 변경하지 않았다.
