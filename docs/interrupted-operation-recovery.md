# Interrupted operation recovery

## 기본 정책

중단 작업은 앱 시작 때 자동 **검사**하되 파일 이동·복사·제거·기록 복구는 사용자 선택 없이 실행하지 않는다. 기본 선택지는 이어서 정리, 이전 이동 되돌리기, 나중에다. 화면·캐릭터는 같은 진단 결과를 표현할 수 있으며 코어가 표시 방식이나 캐릭터를 알 필요는 없다.

읽기 전용 조회와 명시적 전체 재개/되돌리기 백엔드를 구현했다. 현재 실행 가능한 범위는 모든 단계의 실제 위치가 확실하고 개별 전송이 미해결 상태가 아닌 작업이다. 새 시작 조회·선택 안내를 앱 조립부에 연결하지 않았으며 기존 앱의 구형 RecoveryService 동작도 교체하지 않았다.

## 구현된 조회 계약

`InspectInterruptedPlanUseCase`는 외부 소유의 이력·전송 저널·읽기 전용 파일 검사·해시·볼륨 조회 포트를 빌려 받는다. 이동기나 원본 제거 포트를 받지 않으며 이력·저널은 const 참조로 받아 갱신하지 않는다.

- `execute(planId)`: 새로 읽은 작업 하나를 검사한다.
- `inspectAll()`: 미완료 목록에서 Executing, RollingBack, NeedsRecovery만 골라 검사한다. 초안·승인 대기·정상 완료 작업은 제외한다. 목록 조회 뒤 정상 상태로 바뀐 작업도 제외한다.
- NeedsRecovery는 직전 실행/되돌리기 방향을 이력에서 조회한다. 방향을 확인할 수 없으면 후보를 차단한다.
- 서명·지원 형식·절대 경로·단계 ID·원본 객체/해시 증거를 검사한다. v2는 실제 볼륨 계약도 재확인한다. 전역 증거가 틀리면 파일 경로를 조회하지 않는다.

결과에는 작업 ID, 현재/중단 직전 상태, 단계별 진단, 개수, 정방향 재개/되돌리기 후보와 이유가 들어 있다. 나중에는 어떤 변경도 요청하지 않고 미해결 작업을 그대로 보존하는 선택이다.

| 단계 상태 | 의미 |
| --- | --- |
| Pending | 승인 원본 객체·내용·시각이 그대로 있고 목적지는 올바른 볼륨에서 비어 있음 |
| Moved | 이름 변경의 원래 객체 또는 완료된 복사의 기록된 최종 객체가 목적지에 있음 |
| Restored | 되돌리기 증거와 실제 복원 결과가 일치함 |
| Skipped | 승인 계획에서 건너뛰도록 정해진 단계 |
| NeedsAttention | 부분 복사, 완료 기록 누락, 충돌, 변경, 접근 실패, 기록 불일치 등 개별 확인이 필요함 |

복사는 `InspectTransferRecoveryUseCase`의 원본·임시·최종 세 위치 진단을 재사용한다. 완전한 완료 기록이 없는 복사는 최종 파일이 있어도 Moved로 세지 않는다. 역전송은 유일한 완료 정방향 결과의 객체·내용·수정 시각에 연결되어야 한다. 복사본은 원래 객체 ID가 달라지므로 이름 변경과 같은 객체 비교로 처리하지 않는다. 서로 다른 계획의 전송 기록은 이번 작업의 증거로 사용하지 않는다.

같은 이름/내용의 다른 객체, 잘못된 볼륨, 여러 전송 시도, 조회 실패, 기록·실제 파일 불일치는 보수적으로 차단한다. 되돌리기 중 원위치 파일은 있지만 기록상 대기/복원 여부를 구분할 수 없다면 임의로 Pending이나 Restored로 추측하지 않는다.

## 선택지의 의미

`RecoveryReadiness`는 실행 가능 확정값이 아니라 **관찰 시점의 후보 판단**이다.

| 값 | 의미 |
| --- | --- |
| NeedsRevalidation | 후보가 있지만 선택 후 작업 잠금 아래에서 현재 승인·설정·규칙·파일·볼륨을 다시 검사해야 함 |
| NeedsStepRecovery | 중단된 개별 전송의 증거/파일/기록을 먼저 명시적으로 복구해야 함 |
| Blocked | 충돌·변경·불확실한 기록 등으로 후보를 제안할 수 없음; 이유를 함께 반환 |
| NotApplicable | 현재 해당 행동으로 처리할 파일이 없음 |

되돌리기를 시작했거나 일부 파일이 이미 복원되었다면 정방향으로 몰래 전환하지 않는다. 모든 파일이 이동했더라도 전체 완료 기록이 남았다면 조회는 Executing을 그대로 보존하고 명시적 기록 확인 후보만 반환한다. 조회 결과를 복구 승인이나 파일 변경 권한으로 저장/재사용하면 안 된다.

## 명시적 전체 복구 실행

`RecoveryRequest`는 작업 ID·표시 당시 승인 해시·Resume/Rollback/Later 선택을 전달한다. 앱 조립부는 외부 포트와 `InspectInterruptedPlanUseCase`, `RecoverInterruptedPlanUseCase`, 기존 `SafeExecutor`를 소유하고 연결해야 한다. 코어는 화면이나 캐릭터를 생성하지 않는다.

`InterruptedOperationRecoveryService`가 기존 실행/복구와 같은 시스템 잠금을 획득한다. `RecoverInterruptedPlanUseCase`는 승인 해시·현재 설정/규칙 버전 및 리비전 → 새 전체 조회 → 실행 포트·보호 경로 검사 → 원자적 선택 기록 → 다시 파일/설정/규칙 검사 → 기존 실행기로 순서대로 진행한다. Later는 잠금·파일 조회·DB 기록 없이 성공을 반환하고 미해결 상태를 보존한다.

`IHistoryRepository::beginRecovery`의 기본 구현은 지원하지 않음을 반환한다. SQLite 구현은 승인된 작업의 현재 해시/서명·상위 상태·모든 단계 ID/기존 상태를 비교한다. 선택에 따른 Executing/RollingBack과 관찰된 Planned/Applied/RolledBack/Skipped 복원, `recovery_choice_recorded` 감사, `plan_status_changed` 방향 사건을 한 트랜잭션에 저장한다. 선택 감사에는 승인 해시·선택·이전/이후 작업 상태·각 단계의 이전/이후 상태가 남는다. 실패하면 모두 롤백하며 원래 승인 해시·지문·목적지·건너뛰기 결정은 바꾸지 않는다. Schema v8·규칙 JSON v3·승인 계획 v2는 그대로다.

재개는 Applied를 다시 실행하지 않고 Planned만 기존 승인 순서로 실행한다. 기존 `SafeExecutor`의 최초 실행과 재개는 같은 단계 이동·안전 재검사·확실한 실패의 역순 보상·완료 기록을 공유한다. 되돌리기는 남은 Applied만 전체 사전 검사 후 역순 복원하며, 아직 시작하지 않은 원본은 건드리지 않는다. 파일 복원은 끝났지만 RollingBack만 남은 경우에는 명시적 선택 후 전체 완료 기록만 끝낸다. 완료된 요청을 반복하면 중단 작업이 아니므로 거부한다.

이 계층은 **NeedsStepRecovery를 자동으로 해석해서 부분 복사를 이어 쓰거나 삭제하지 않는다**. `recovery.step_resolution_required`로 멈추고 파일·기록을 보존한다. 기존 개별 복구 유스케이스로 미해결 단계를 명시적으로 처리한 뒤 전체 조회와 선택을 다시 해야 한다. 그 개별 선택과 전체 복구를 묶는 조율 및 혼합 배치 프로세스 강제 종료 시험은 남아 있다. 설정/규칙이 달라졌다면 원래 승인으로 조용히 계속하지 않고 `recovery.configuration_changed`를 반환한다.
