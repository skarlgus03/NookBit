# Interrupted operation recovery

## 기본 정책

새 [다운로드 표식 보존 정책 1](download-marker-copy.md)도 원본이 남은 정방향 부분 복사·최종 확정·제거 재개를 지원한다. 원본과 복사본의 표식이 달라지거나 읽을 수 없으면 파일을 보존·차단한다. 원본 없는 미완료 기록에는 영구 저장된 표식 증거가 없어 자동 완료 확정을 차단한다. 중단 역전송과 표식 임시 파일 정리는 아직 미지원이다. 정상 완료 뒤 명시적 되돌리기는 표식을 보존한다. 기본 정책 0의 기존 복구 계약은 유지한다.

새 [MetadataRename](same-volume-fast-move.md) 계약의 중단 작업은 이번 단계에서 자동 재개/되돌리기 후보를 차단하고 별도 확인 안내만 제공한다. 정상/부분 실패 완료 작업의 성공 부분 되돌리기는 가능하다. 아래 전체 중단 복구는 기존 내용 해시 기반 Rename/VerifiedCopy 작업의 계약이다.

중단 작업은 앱 시작 때 자동 **검사**하되 파일 이동·복사·제거·기록 복구는 사용자 선택 없이 실행하지 않는다. 기본 선택지는 이어서 정리, 이전 이동 되돌리기, 나중에다. 화면·캐릭터는 같은 진단 결과를 표현할 수 있으며 코어가 표시 방식이나 캐릭터를 알 필요는 없다.

앱의 전체 작업 조회는 백그라운드 실행기와 작업 스레드 전용 DB 연결을 사용한다. 느린 내용 검사 중에도 화면 이벤트를 처리하고, 조회 중 중복 요청·이전 결과의 실행을 차단한다. 구형 v1의 기록만 확정하는 호환 조회는 기존 동기 경로다.

읽기 전용 조회와 명시적 전체 재개/되돌리기 백엔드를 앱에 연결했다. 정방향은 지원하는 개별 전송부터 복구하고, 되돌리기는 온전한 원본과 소유한 부분 임시 파일이 남은 전송을 보존한 채 이미 이동된 파일만 복원한다. 보존 임시 파일은 이동 복원 완료 후에도 확인 대상으로 남는다. 시작 시 구형 RecoveryService의 자동 기록 정합화를 실행하지 않는다. 구형 v1의 명시적 기록 확인은 호환용으로 유지하며 v2에는 적용하지 않는다.

## 앱 선택 화면 (2026-10-06)

`RecoveryController`는 main에서 주입한 `IInterruptedOperations`로 작업별 개수·파일 경로·상태·선택 차단 이유를 표시한다. 파일 일꾼과 전체 복구 유스케이스는 main에서 소유한다. 화면의 선택 가능 여부는 `checkChoice`와 실행이 공유하는 읽기 전용 사전 검사로 판단한다.

- 시작·새로고침은 조회만 한다. 이어서 정리/되돌리기는 표시 당시 승인 해시를 담아 별도 확인창을 띄우고 확인 후에만 실행한다.
- 확인 취소와 나중에는 파일·기록을 바꾸지 않는다. 나중에는 확인 대상을 남긴다. 중복 확인으로 같은 실행을 반복하지 않는다.
- 확인 뒤에도 공유 작업 잠금 아래 설정·활성 규칙·승인·현재 파일 상태를 다시 검사한다. 설정 변경이나 미지원 복사 시작 전/부분 역전송은 차단한다. 조회 실패 시 낡은 선택 버튼도 제거한다.
- 현재 설정은 앱이 수락한 목적지와 공통 충돌 정책을 반영한 RuntimeSettingsRepository로 공급한다. 승인 해시를 맞추기 위해 과거 설정을 추측하지 않는다.
- 성공/실패 후 기록과 대기 목록 상태를 새로 읽는다. 완료된 재개 작업의 이동 파일만 대기 목록에서 제거한다.
- 부분 보존 되돌리기는 이동 복원 완료와 별도 임시 경로 확인을 구분한다. 보존 부분 파일의 별도 승인 정리 화면, 정확한 진행률·안전 취소 UI, 캐릭터는 아직 없다. 파일 실행은 백그라운드에서 처리하며 정리 전 검사 준비·승인도 백그라운드이며 시작 복구 조회는 아직 동기다.

자동 테스트 19/19 및 실제 두 볼륨 경계/전송 복구/부분 보존/Qt 통합 33/33이 통과했다. Qt 통합 11개 중 새 선택 경로 6개는 재개·되돌리기·확인 후 설정 변경·부분 재개·부분 보존 되돌리기·미지원 시작 차단이다. 기본 컨트롤러 테스트는 취소·나중에·낡은 승인·중복 확인·조회 실패도 검사한다. 실제 창 열기/닫기는 QML smoke로 검증했으며 사용자의 시각적 조작 테스트와 구분한다.

## 단계 증거 보존 회귀 수정 (2026-10-06)

코드 점검에서 두 상태 손실을 실제 임시 파일·SQLite로 먼저 재현하고 수정했다.

- 구형 시작 복구가 전송 저널 없는 v2 Rename 되돌리기를 만났을 때 RolledBack/Applied를 NeedsRecovery로 덮어쓰던 경로를 분리했다. 두 번의 시작 검사에서도 상태·계획 내용을 유지하고, 새 진단은 1개 Restored/1개 Moved를 판별해 명시적 남은 되돌리기를 마무리한다.
- 새 실행기의 오류 표시가 아직 시작하지 않은 Planned 단계까지 덮어쓰던 경로를 수정했다. Planned/Skipped/RolledBack은 보존한다. v1/v2 각각에서 1개 이동·2개 미시작 상태의 되돌리기에 점유 충돌을 주입하고, 점유를 해소하면 1개 Moved/2개 Pending으로 다시 진단해 미시작 원본을 건드리지 않고 완료한다.

상태를 보존한 v2 Executing/RollingBack이 구형 화면 목록에서 사라지는 연동도 막았다. requiresWholeRecovery 표시로 목록·시작 경고를 유지하며 기존 resolveCase는 v2를 변경하지 않는다. 전체 재개/되돌리기 버튼을 새로 연결한 것은 아니다. Qt 컨트롤러 회귀는 실제 시작 검사→목록 새로고침→거부되는 구형 확인 요청 뒤에도 RollingBack/RolledBack과 원본이 유지되는지 확인한다.

기존 자동 묶음 19/19과 실제 두 볼륨 강제 종료 경계 5개·부분 보존 되돌리기 6개·앱 통합 실행 5개를 별도로 재실행해 통과했다. 추가한 4개 시나리오는 기존 recovery_service_tests와 preview_controller_tests에 포함된다. 승인 계획 v2·규칙 JSON v3·SQLite 스키마 v8은 변경하지 않았다.

## 구현된 조회 계약

`InspectInterruptedPlanUseCase`는 외부 소유의 이력·전송 저널·읽기 전용 파일 검사·해시·볼륨 조회 포트를 빌려 받는다. 이동기나 원본 제거 포트를 받지 않으며 이력·저널은 const 참조로 받아 갱신하지 않는다.

- `execute(planId)`: 새로 읽은 작업 하나를 검사한다.
- `inspectAll()`: 미완료 목록에서 Executing, RollingBack, NeedsRecovery만 골라 검사한다. 초안·승인 대기·정상 완료 작업은 제외한다. 목록 조회 뒤 정상 상태로 바뀐 작업도 제외한다.
- NeedsRecovery는 직전 실행/되돌리기 방향을 이력에서 조회한다. 방향을 확인할 수 없으면 후보를 차단한다.
- 서명·지원 형식·절대 경로·단계 ID·원본 객체/해시 증거를 검사한다. v2는 실제 볼륨 계약도 재확인한다. 전역 증거가 틀리면 파일 경로를 조회하지 않는다.

결과에는 작업 ID, 현재/중단 직전 상태, 단계별 진단, 개수, 정방향 재개/되돌리기 후보와 이유가 들어 있다. 나중에는 어떤 변경도 요청하지 않고 미해결 작업을 그대로 보존하는 선택이다.

| 단계 상태 | 의미 |
| --- | --- |
| Pending | 승인 원본 객체·내용·시각이 그대로 있고 목적지는 올바른 볼륨에서 비어 있음 |
| Moved | 이름 변경의 원래 객체 또는 완료된 복사의 기록된 최종 객체가 목적지에 있음 |
| Restored | 되돌리기 증거와 실제 복원 결과가 일치함 |
| Skipped | 승인 계획에서 건너뛰도록 정해진 단계 |
| NeedsAttention | 부분 복사, 완료 기록 누락, 충돌, 변경, 접근 실패, 기록 불일치 등 개별 확인이 필요함 |
| Preserved | 명시적 되돌리기 선택으로 원본과 소유한 부분 임시 파일을 건드리지 않고 보존함; 별도 확인 필요 |

복사는 `InspectTransferRecoveryUseCase`의 원본·임시·최종 세 위치 진단을 재사용한다. 완전한 완료 기록이 없는 복사는 최종 파일이 있어도 Moved로 세지 않는다. 역전송은 유일한 완료 정방향 결과의 객체·내용·수정 시각에 연결되어야 한다. 복사본은 원래 객체 ID가 달라지므로 이름 변경과 같은 객체 비교로 처리하지 않는다. 서로 다른 계획의 전송 기록은 이번 작업의 증거로 사용하지 않는다.

같은 이름/내용의 다른 객체, 잘못된 볼륨, 여러 전송 시도, 조회 실패, 기록·실제 파일 불일치는 보수적으로 차단한다. 되돌리기 중 원위치 파일은 있지만 기록상 대기/복원 여부를 구분할 수 없다면 임의로 Pending이나 Restored로 추측하지 않는다.

## 선택지의 의미

`RecoveryReadiness`는 실행 가능 확정값이 아니라 **관찰 시점의 후보 판단**이다.

| 값 | 의미 |
| --- | --- |
| NeedsRevalidation | 후보가 있지만 선택 후 작업 잠금 아래에서 현재 승인·설정·규칙·파일·볼륨을 다시 검사해야 함 |
| NeedsStepRecovery | 중단된 개별 전송의 증거/파일/기록을 먼저 명시적으로 복구해야 함 |
| Blocked | 충돌·변경·불확실한 기록 등으로 후보를 제안할 수 없음; 이유를 함께 반환 |
| NotApplicable | 현재 해당 행동으로 처리할 파일이 없음 |

되돌리기를 시작했거나 일부 파일이 이미 복원되었다면 정방향으로 몰래 전환하지 않는다. 모든 파일이 이동했더라도 전체 완료 기록이 남았다면 조회는 Executing을 그대로 보존하고 명시적 기록 확인 후보만 반환한다. 조회 결과를 복구 승인이나 파일 변경 권한으로 저장/재사용하면 안 된다.

## 명시적 전체 복구 실행

`RecoveryRequest`는 작업 ID·표시 당시 승인 해시·Resume/Rollback/Later 선택을 전달한다. 앱 조립부는 외부 포트와 `InspectInterruptedPlanUseCase`, `RecoverInterruptedPlanUseCase`, 기존 `SafeExecutor`를 소유하고 연결해야 한다. 코어는 화면이나 캐릭터를 생성하지 않는다.

`InterruptedOperationRecoveryService`가 기존 실행/복구와 같은 시스템 잠금을 획득한다. `RecoverInterruptedPlanUseCase`는 승인 해시·현재 설정/규칙 버전 및 리비전 → 새 전체 조회 → 실행 포트·보호 경로 검사 → 원자적 선택 기록 → 다시 파일/설정/규칙 검사 → 기존 실행기로 순서대로 진행한다. Later는 잠금·파일 조회·DB 기록 없이 성공을 반환하고 미해결 상태를 보존한다.

`IHistoryRepository::beginRecovery`의 기본 구현은 지원하지 않음을 반환한다. SQLite 구현은 승인된 작업의 현재 해시/서명·상위 상태·모든 단계 ID/기존 상태를 비교한다. 선택에 따른 Executing/RollingBack과 관찰된 Planned/Applied/RolledBack/Skipped 복원, `recovery_choice_recorded` 감사, `plan_status_changed` 방향 사건을 한 트랜잭션에 저장한다. 선택 감사에는 승인 해시·선택·이전/이후 작업 상태·각 단계의 이전/이후 상태가 남는다. 실패하면 모두 롤백하며 원래 승인 해시·지문·목적지·건너뛰기 결정은 바꾸지 않는다. Schema v8·규칙 JSON v3·승인 계획 v2는 그대로다.

재개는 Applied를 다시 실행하지 않고 Planned만 기존 승인 순서로 실행한다. 기존 `SafeExecutor`의 최초 실행과 재개는 같은 단계 이동·안전 재검사·확실한 실패의 역순 보상·완료 기록을 공유한다. 되돌리기는 남은 Applied만 전체 사전 검사 후 역순 복원하며, 아직 시작하지 않은 원본은 건드리지 않는다. 파일 복원은 끝났지만 RollingBack만 남은 경우에는 명시적 선택 후 전체 완료 기록만 끝낸다. 완료된 요청을 반복하면 중단 작업이 아니므로 거부한다.

정방향 NeedsStepRecovery는 `IInterruptedTransferResolver` 연결 시 아래 지원 경계를 사용한다. 되돌리기는 아래 부분 보존 조건만 별도로 허용하며, 그 외 미해결 전송은 차단한다. 설정/규칙이 달라졌다면 원래 승인으로 조용히 계속하지 않고 `recovery.configuration_changed`를 반환한다.

## 개별 전송 복구 → 전체 정방향 재개

조립부가 `ResumeInterruptedTransferUseCase`를 외부 포트로 만들고 전체 복구 유스케이스에 `IInterruptedTransferResolver`로 빌려준다. 구체 파일 일꾼을 새로 만들거나 UI를 호출하지 않는다. 지원하는 모든 미해결 단계의 경계를 읽기 전용으로 검사하고, 기존 실행기의 서비스 구성/경로 검사도 통과해야 선택을 기록한다.

선택 감사 트랜잭션은 미해결 VerifiedCopy의 상태만 IntentRecorded로 복원할 수 있다. 원래 상태도 IntentRecorded/NeedsRecovery여야 하며 되돌리기에는 허용하지 않는다. 승인 해시·지문·경로·건너뛰기 결정은 그대로다. 모든 원본의 기존 Planned/Applied/Skipped 상태와 선택 감사는 함께 저장된다. 감사 실패에는 복구 파일 작업을 시작하지 않는다.

| 관찰 경계 | 실행 경로 |
| --- | --- |
| PartialCopy | 보호된 원본 전체/앞부분 검사 → 이어쓰기/전체 검증 → 임시 확정 → 원본 제거/완료 |
| VerifiedStaging | 재개 검증이 이미 끝났으면 임시 확정, 일반 CopyVerified/CommitIntent 중단이면 중단 감사 후 보호된 전체 재검증부터 시작 |
| CommitNotRecorded | 두 파일을 보호해 확정 기록만 복구 → 별도 원본 제거/완료 |
| CommittedSourceRetained | 두 복사본 재검증 → 복구 제거 의도 저장 → 원본 제거/완료 |
| SourceAbsentAfterRemoveIntent | 보호된 최종 결과 검사 → 파일 재삭제 없이 완료 기록만 복구 |

일반 검증된 임시 파일은 CopyVerified/CommitIntent에서 명시적 NeedsRecovery 사건을 남기고 기존 이어쓰기 검증 절차를 사용한다. 기록된 stage 객체를 다시 검증하며, 새 시도나 다른 임시 파일을 만드는 폴백은 없다. 각 경계마다 새 진단과 승인 연결을 확인하고 최대 네 번의 경계 처리로 완료를 확인한다. 제거 기록 누락의 실제 의도 증명은 기존 저널 재생과 원자적 완료 복구가 담당한다. 별도 recoveryRemovalIntent가 기록된 원본 부재도 같은 진단 경계로 표시한다.

전체 조율기는 선택 전·선택 저장 후·개별 복구마다 원래 승인 내용/단계 ID·설정·규칙을 재검사한다. 개별 복구가 하나라도 실패하면 남은 전체 실행을 시작하지 않는다. 모두 끝나면 전체 파일 상태를 다시 읽고 기존 실행기로 Pending만 처리한다. 마지막 전송이 전체 계획을 Completed로 끝냈다면 `inspectAfterResume`로 실제 완료·미해결 없음·원래 승인 유지를 확인하고 완료 실행기를 다시 호출하지 않는다. 일반 시작 조회는 여전히 완료 작업을 제외한다.

NoCopyObserved의 새 복사 재시작, 변경/미소유/접근 실패/모호한 기록, 정리 의도가 있는 전송은 이 정방향 조율 대상이 아니다. 부분 복사 앞부분 손상은 보호된 재개 검사에서 차단하며 선택 감사는 보존하지만 원본·손상된 임시 파일·나머지 파일을 옮기거나 지우지 않는다. 앱 시작이나 조회만으로 이 경로를 호출하지 않는다.

## 부분 복사를 보존하는 되돌리기

`canPreservePartialTransfer`는 원본 Matches·임시 ObjectOnly·최종 Missing인 정방향 PartialCopy만 허용한다. 실제 원본 객체·전체 해시·시각·볼륨은 승인과 같아야 하고, 임시 파일은 기록된 소유 객체여야 한다. 확정/제거/정리 의도나 전체 검증 완료가 있는 전송은 이 정책에 섞지 않는다. 부분 파일의 내용을 완성하거나 삭제하지 않으므로 이 검사 자체가 임시 파일 정리 권한은 아니다.

전체 되돌리기 선택은 해당 단계만 Planned로 두고 `PreservedTransfer`의 시도 ID·단계 ID·임시 경로를 선택 감사의 `preservedTransfers`에 함께 원자적으로 저장한다. SQLite는 현재 승인·단계와 실제 정방향 부분 전송 레코드의 경로/소유 연결을 확인한다. 기존 보존 등록을 다음 선택에서 누락할 수 없으며 정방향으로 전환하지 않는다. 선택 저장 후 다시 검사해야 기존 실행기의 Applied 역순 복원을 시작한다. 원본·임시 파일·개별 전송 단계/이어쓰기 상태는 그대로 유지한다.

이동 부분의 완료는 RolledBack으로 기록하지만 보존 임시 파일의 확인은 끝난 것으로 처리하지 않는다. `preservedTransfers`·`preservedTransferPlans` 읽기 포트와 `inspectAll`은 완료된 되돌리기도 확인 목록에 포함한다. `preserved` 개수와 단계 이유를 반환하며, 임시 객체가 교체되거나 저널 증거가 사라지면 등록은 보존하고 NeedsAttention으로 표시한다. 이 목록을 읽는 동작은 기록/파일을 변경하지 않는다. UI/캐릭터는 이동 복원 완료와 임시 파일 확인 필요를 따로 표시해야 한다.

되돌리기 도중 충돌하면 이미 복원한 단계는 유지하고 NeedsRecovery로 중단한다. 보존 등록은 선택 감사에 이미 저장되어 있으므로 재시작에서도 남는다. 자동 임시 삭제는 제공하지 않는다. 이동 복원이 RolledBack으로 끝난 뒤의 별도 승인 정리는 아래 계약을 따른다. Schema v8과 승인/규칙 형식은 바꾸지 않았다.

## 보존 부분 파일의 승인 기반 정리

`CleanupPreservedStagingUseCase`와 공유 시스템 작업 잠금 진입점 `PreservedStagingCleanupService`를 제공한다. inspect(planId, attemptId)는 파일/DB를 변경하지 않고 승인 계획 해시와 부분 임시 객체의 ID·전체 SHA-256·크기·수정 시각을 반환한다. execute는 조회 결과에 명시적 approved=true를 붙인 요청만 받는다. 오래된 해시나 지문은 재조회·재승인이 필요하다. UI/시작 자동 호출에는 아직 연결하지 않았다.

범위는 RolledBack으로 이동 복원을 끝낸 계획, Planned인 부분 복사 단계, 정방향 보존 등록, StagingCreated/Cancelled/Failed/NeedsRecovery 증거다. CopyResume·StagingCommit·기존 StagingCleanup·원본 제거/복구 완료 증거가 없는 부분 객체만 받는다. 기록된 객체와 같은 부분 임시 파일의 크기는 원본보다 작아야 한다. 이름만 같은 파일, 소유 증거 없는 파일, 계속 되돌리는 중인 계획, 전체 검증 복사본은 이 경로로 정리하지 않는다.

1. 승인 해시·단계 경로·원본 지문·단일 정방향 시도·보존 등록을 다시 묶어 검사한다.
2. Windows 어댑터가 원본·임시 객체·부모를 보호한다. 실제 승인 GUID/NTFS, 원본 전체 내용, 승인한 부분 지문과 원본 앞부분의 바이트 일치를 검사한다. 읽기 전용/재분석/ADS/다중 링크 등 비지원 파일은 보존한다. 최종 경로는 없어야 한다.
3. 보호 세션을 유지한 채 `preserved_cleanup_intent`를 먼저 원자적으로 저장한다. 실패에는 삭제하지 않는다.
4. 같은 보호된 임시 객체만 핸들로 제거하고 부재·원본 보존·최종 경로 부재를 재확인한 뒤 `preserved_cleanup_removed`를 기록한다.

삭제 뒤 완료 감사가 실패하면 의도와 승인 지문을 남긴다. 새 SQLite 연결에서 동일 승인·온전한 원본·임시/최종 경로 부재를 검사한 뒤 명시적 재시도는 완료 감사만 기록한다. 임시 경로에 다른 객체가 생겼으면 제거하지 않고 차단한다. 이전 의도 없이 파일이 없다는 사실만으로 정리 완료를 인정하지 않는다. 손상된 감사/소유 기록도 명시적 오류로 반환한다.

기존 보존 등록과 정방향 전송의 phase/copyResume는 변경하지 않는다. 계획·단계 상태와 승인 해시도 그대로다. 완료 감사가 저장된 항목만 시작 확인 목록에서 제외하며 보존/정리 감사 이력은 삭제하지 않는다. SQLite 스키마 v8·승인 계획 v2·규칙 JSON v3는 유지한다. 기본 안전 동작은 거부/보존이며 속성 강제 변경·자동 삭제·경로 재귀 삭제는 제공하지 않는다.
