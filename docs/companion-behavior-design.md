# 알림 · Interact · 행동 계약

## 범위와 현재 구현

알림은 공통 창구의 등록·발생 상태·표시 허용 정책과 간단한 설정 페이지까지 구현한다.
Interact와 행동은 아래 계약 초안만 정의한다. 반응 큐, 우선순위 편집,
일회 반응의 수명, 자율 이동, 동적 플러그인/모듈 로딩은 이번 구현에 포함하지 않는다.
ImagePack v1 포맷과 기존 resting/calling/working 바인딩은 유지한다.

## 책임 구분

| 구분 | 의미 | 설정 위치 |
| --- | --- | --- |
| 기능/모듈 | 감시·정리 등 실제 일을 수행 | 추후 모듈 관리 |
| 알림 | 발생한 사실과 사용자에게 알릴 내용 | 알림 페이지 |
| Interact | 사용자가 컴패니언에 건네는 상호작용 요청 | 컴패니언 관리 |
| 행동 | 상황과 환경에 따라 유지·선택하는 기본 표현 | 컴패니언 관리 |
| 표시 수단 | 컴패니언 말풍선, 추후 트레이 등 | 표시 수단별 설정 |

알림 끄기는 기능 중지·기록 삭제·컴패니언 숨기기와 다르다.
작업 중이라는 사실도 알림과 분리하여 유지한다. 알림을 꺼도 작업 모습은 유지될 수 있다.
이동 최종 확인·복구 승인 등 업무 절차의 필수 입력 화면은 알림 끄기의 대상이 아니다.

## 알림: 구현된 v1 데이터

`INotificationChannel`은 Qt·컴패니언·파일 정리를 모르는 공통 입력 창구다.
현재 호출은 수신 어댑터의 소유 스레드에서 수행한다. 포트 자체는 스레드 전환을 제공하지 않는다.

### 종류 등록 (`NotificationType`)

| 필드 | 의미 |
| --- | --- |
| id | 안정적인 알림 종류 ID. 예: `file.offer` |
| sourceId | 제공 기능 ID. 예: `folder-watch` |
| sourceName | 설정에 표시할 제공 기능 이름 |
| name / description | 종류의 사용자용 이름과 설명 |
| defaultEnabled | 설정이 없을 때 표시 허용 여부 |

ID는 영문·숫자·점·밑줄·하이픈만 사용하며 1–160자다. 등록 ID는 중복될 수 없다.
현재는 조립부에서 등록한다. 새 기능은 종류를 등록하면 UI 목록에 자동으로 나타난다.
UI에 종류별 버튼이나 조건 분기를 추가하지 않는다. 이는 알림 종류 등록이며 기능 모듈 로더가 아니다.

### 발생 상태 (`NotificationUpdate`)

| 필드 | 의미 |
| --- | --- |
| typeId | 먼저 등록한 종류 ID |
| instanceId | 제공 기능이 관리하는 개별 알림 ID. 1–256자, NUL 불가 |
| active | true: 발생/갱신, false: 해결/철회 |
| title / message | 알릴 사실의 제목과 본문 |

같은 `(typeId, instanceId)`의 true는 새 항목을 쌓지 않고 갱신한다.
동일 내용 반복 전달은 표시 담당자에게 다시 알리지 않는다.
해제는 source가 false를 보냄으로써 처리한다. 현재 시간 기반 자동 만료는 없다.

### 표시 정책과 수명

`NotificationCenter`는 등록·발생 사실·표시 허용 여부를 별도로 관리한다.
표시를 꺼도 활성 사실은 남는다. 꺼둔 사이 갱신/해제도 계속 반영한다.
다시 켜면 현재 유효한 내용만 전달하고 해결된 알림은 재생하지 않는다.
`NotificationController`는 값과 변경 신호를 UI/표시 어댑터에 제공할 뿐 특정 표시 수단을 호출하지 않는다.

설정은 종류 ID별 `notifications/types/<id>/enabled`에 저장한다.
종류 목록이나 활성 알림 본문은 사용자 설정에 저장하지 않는다.
재실행 시 종류 등록과 함께 설정을 복원하며, 활성 사실은 제공 기능이 다시 전달한다.
저장 실패 시 표시 정책을 바꾸지 않고 오류를 표시한다.

현재 등록 종류는 폴더 감시의 `file.offer`(정리 제안)이다.
감시 → 공통 알림 창구 → 표시 필터 → 조립부의 컴패니언 어댑터 순서로 전달한다.
파일 작업 중 상태는 별도의 활동 입력이며 알림 스위치에 묶지 않는다.
현재 컴패니언은 기존 Attention 표현을 사용하며, 다중 알림의 반응 큐는 후속 단계다.

## Interact: 후속 구현 계약 초안

알림과 달리 사용자가 컴패니언을 대상으로 시작한 상호작용이다.
아래 이름과 데이터는 설계 계약이며 아직 C++ 자료형·창구·관리자를 추가하지 않았다.
기존 캐릭터 창 이동과 말풍선 버튼 동작도 이 계약으로 교체한 상태가 아니다.

### 종류와 요청

종류 등록과 개별 요청을 분리한다. 종류는 제공 기능이 정의하고 요청 ID는 입력 담당자가 발급한다.

| 종류 정의 | 의미 |
| --- | --- |
| typeId / sourceId | 안정적인 종류 ID와 제공 기능 ID |
| name / description | 사용자에게 표시할 이름과 설명 |
| inputMode | 일회 입력 또는 연속 입력 |
| payload 계약 | 이 종류에 필요한 값과 검증 규칙 |

| 요청 데이터 | 의미 |
| --- | --- |
| instanceId | 한 번의 상호작용 식별자. 연속 입력의 시작부터 종료까지 유지 |
| typeId | 등록된 상호작용 종류. 제공 기능은 등록 정보에서 확인 |
| targetId | 팩 ID와 구분되는 대상 컴패니언 인스턴스 ID |
| phase | Invoke / Begin / Update / End / Cancel |
| context | 발생 당시 기본 행동 ID와 현재 일시 반응 ID(없으면 생략) |
| payload | 위치·먹이 ID 등 종류가 정의한 입력값 |

`context`는 발생 당시 상황을 설명하는 값이며 실행 권한을 보장하지 않는다.
관리자는 처리 시점에 대상 존재·기능 활성 여부·현재 상황을 다시 확인한다.
종류가 정의한 값만 검증해 받고 임의 코드·콜백·다른 작업자 포인터를 전달하지 않는다.
위치가 필요한 종류는 좌표계를 명시하며 화면 픽셀을 모든 종류의 공통 좌표로 가정하지 않는다.

공통 관리자는 종류 조회·입력 검증·세션 수명을 맡고, 실제 효과는 등록된 처리 창구에 맡긴다.
조립부가 종류와 처리 구현을 연결하며 관리자가 개별 기능 구현을 생성하거나 참조하지 않는다.
새 종류마다 공통 관리자의 조건 분기를 늘리는 대신 등록 정보를 추가한다.
동적 모듈 로딩은 별도 과제이며 이 등록 구조 자체가 플러그인 로더를 의미하지 않는다.

### 첫 기준 사례

| 종류 ID(초안) | 의미 | 단계 | 종류별 입력 |
| --- | --- | --- | --- |
| companion.click | 컴패니언을 한 번 클릭 | Invoke | 필요한 경우 접촉 위치 |
| companion.drag | 컴패니언을 잡아 옮기기 | Begin → Update → End/Cancel | 이동 입력 |
| companion.pet | 컴패니언 쓰다듬기 | Begin → Update → End/Cancel | 접촉 위치와 움직임 |

이 세 가지로 계약을 먼저 검증한다. 먹이 주기는 후속 기능이 같은 등록·요청 경로로 제공한다.
특정 애니메이션 이름을 요청에 고정하지 않는다. 처리 결과와 상황에 맞는 반응 cue를
표현 쪽에서 선택하고, 캐릭터팩이 그 cue에 사용할 그림을 결정한다.

### 입력 판정과 세션 수명

물리적인 마우스 입력을 의미 있는 요청으로 바꾸는 입력 판정 담당자를 둔다.
공통 관리자가 Qt 마우스 이벤트나 특정 창을 직접 알지 않도록 한다.

1. 누르는 즉시 클릭을 발행하지 않는다. 이동 조작으로 확정되지 않고 놓았을 때 클릭으로 확정한다.
2. 한 번의 포인터 조작은 하나의 상호작용 종류가 소유한다. 끌기 종료가 클릭을 추가 발생시키지 않는다.
3. 끌기와 쓰다듬기는 같은 움직임을 동시에 해석하지 않는다. 별도 모드·명시적 입력 등 구별 가능한 진입 조건을 먼저 둔다. 구체 버튼·키·판정 임계값은 UI 연결 시 결정한다.
4. 연속 입력은 수락된 Begin 뒤에만 Update/End를 받으며 마지막에 End 또는 Cancel 한 번으로 닫힌다. 종료한 세션의 늦은 입력으로 다시 시작하지 않는다.
5. 포인터 캡처 상실·대상 제거·제공 기능 비활성화 시 세션을 취소하고 임시 입력 상태를 해제한다.
6. 연속 입력의 Update는 최신 상태로 합칠 수 있으며 오래된 움직임을 반응 큐에 계속 쌓지 않는다.

Cancel은 입력 세션의 취소를 뜻한다. 이미 이동한 창 위치나 소모된 자원을 되돌릴지는
각 종류의 효과 계약에서 정한다. 모든 종류에 공통 롤백을 약속하지 않는다.
세션은 실행 중 메모리에만 두며 앱 재실행 후 클릭·쓰다듬기를 재생하지 않는다.

### 처리 결과와 표현

처리 결과에는 요청 ID, Accepted / Completed / Cancelled / Rejected 상태와 이유 코드를 둔다.
일회 요청은 곧바로 Completed 또는 Rejected로 끝날 수 있다.
종류 미등록·기능 비활성·대상 없음·잘못된 입력·현재 수행 불가를 구분한다.
반복된 동일 세션 시작·종료 입력이 효과를 중복 실행하지 않도록 세션을 검사한다.

요청 수신, 기능 처리 완료, 반응 애니메이션 종료는 서로 다른 시점이다.
실행 불가능한 입력은 무기한 대기시키지 않고 거절하며, 사용자 입력에 대한 피드백은 빠르게 돌려준다.
현재는 대기 중 상호작용의 디스크 저장이나 재시도 시스템을 설계하지 않는다.

알림 표시를 꺼도 Interact 자체를 중지하지 않는다. 기능 비활성화는 별도 정책이다.
실제 먹이 소모 등 효과는 해당 기능이 담당하고 컴패니언은 결과에 맞는 표현만 선택한다.
말풍선의 정리 제안 확인 버튼은 업무 명령 진입점이며 일반 캐릭터 클릭과 중복 처리하지 않는다.

예를 들어 쉬는 중 쓰다듬기와 작업 중 쓰다듬기는 같은 종류의 요청이다.
현재 상황에 따라 수락 여부나 표현 길이가 달라질 수 있지만 파일 작업 자체를 중단시키지 않는다.
반응이 끝난 후에는 요청 당시가 아니라 현재 상황에서 기본 행동을 다시 선택한다.

## 행동: 후속 구현 계약 초안

현재 행동은 큐에 쌓인 알림이 아니라 지속되는 기본 표현이다.
상황 입력(작업 중 등)과 자율 행동(쉬기·걷기·앉기)을 구분한다.

- 정의: `behaviorId`, 선택 조건, 애니메이션 cue, 반복/종료 규칙, 중단 가능 여부.
- 현재 상태: 선택한 행동 ID, 시작 시각, 필요 시 진행 위치와 중단/복귀 정보.
- 상황 입력: 제공 기능·활동 ID와 활성 여부. 작업 종료를 알림 반응 종료와 혼동하지 않는다.
- 자율 선택: 허용 조건 안에서만 수행하며 유효하지 않은 이전 행동으로 복귀하지 않는다.

반응이 끝나면 그때의 상황을 다시 판단한다. 작업 중 클릭 반응을 보여준 사이 작업이 끝났다면
예전 작업 모습으로 돌아가지 않고 완료 반응 또는 휴식으로 이어진다.
다중 컴패니언은 표현 컨텍스트의 참가 ID를 확장하여 다루며, 작업자 수나 멀티스레딩과는 별개다.

## 반응 관리: 다음 단계에서 구현할 규칙

현재 기본 행동과 현재 일시 반응, 대기 반응 큐를 분리한다.
알림/Interact는 각각의 정책으로 반응을 요청하고 같은 표시 자원을 조율한다.

1. 표시 여부를 먼저 판단한다. 높은 중요도도 사용자의 알림 끄기를 무시하지 않는다.
2. 같은 중요도는 수신 순서로 처리하고, 같은 인스턴스는 갱신하며 철회/만료 항목은 제거한다.
3. 먼저 보여줄 순서와 현재 반응을 중단할 권한은 별도 정책으로 둔다.
4. 알림 사실이 남는 기간과 말풍선/반응 애니메이션의 표시 기간은 분리한다.
5. 반응 종료 후 현재 상황에 맞는 기본 행동을 다시 선택한다.

중요도(낮음/보통/높음), 중단 정책, 만료/병합 정책과 일회 알림은 이 단계에서 데이터로 확장한다.
현재 종류별 켜기/끄기 UI가 이 설정을 하드코딩하거나 반응 스케줄러를 소유하지 않는다.
